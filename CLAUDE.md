# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Harbor**; a Linux desktop app for running and monitoring multiple Claude Code sessions at once. Since the **"Slate" redesign (2026-07-18, Claude-design handoff)** the main surface is NOT a terminal: a 236px session rail opens sessions as **designed conversation windows** (prompt bubbles → assistant prose → tool-action rows, parsed live from the session's `~/.claude/projects` JSONL transcript) on an adaptive free-form stage (up to **16** open windows: 1 full, 2 split, then an equal-cell grid 2×2 → 3×2 → 3×3 → 4×3 → 4×4, drag a window header to rearrange), driven by one **universal command bar** at the bottom. The command bar's model chip opens a per-session **capability menu** (live models, effort, permission mode, honest fast mode, plugins, live slash commands). A per-window `>_` toggle flips to the real xterm.js terminal (permission prompts live in the pty, not the transcript). It is an **Electron GUI head on a stock, pinned Herdr 0.7.4 daemon**; the GUI never forks or replaces Herdr; it drives Herdr's third-party client surface (`session.snapshot`, `events.subscribe`, and the `herdr terminal session observe|control` byte bridge) for pty control, while conversations render from transcripts.

The Slate design reference (tokens, material, layout) is `design_handoff_harbor_slate/` (Pat's download; tokens are reproduced in `app/src/renderer/styles.css`). The pre-Slate design record is `/home/you/dev/harbor/docs/ARCHITECTURE-v2.md`; still authoritative for the daemon plumbing (bridges, streams, lifecycle), superseded for the renderer. Requirements: `docs/REQUIREMENTS-v2.md`. Build narrative: `docs/SETUP-LOG.md`.

## Commands

All app commands run from `/home/you/dev/harbor/app/` (uses the system Node, built with v22):

```
npm install
npm start            # launch the app (electron .); main is src/main/index.js, it does NOT need a prior build for main-process code, but the renderer must be built (npm run build) unless using dev
npm run dev          # vite dev server (127.0.0.1:5173) + electron with VITE_DEV_SERVER_URL
npm run build        # vite build -> app/dist/ (renderer only)
npm test             # node scripts/test.js: Node built-in --test over every test/**/*.test.js
npm test -- herdr    # filter test files by path substring (runs only test/herdr/*)
npm run test:e2e     # node scripts/e2e.js: build -> notify unit tests -> Playwright Electron suite run TWICE
```

- **`npm run test:e2e` is a two-run gate**: both consecutive Playwright runs must be green or it fails. It (and `scripts/verify-all.js` / `scripts/verify-chrome.js`) ALWAYS runs under `xvfb-run` with the session displays scrubbed; test windows must never open on the live desktop and steal focus. `HARBOR_E2E_HEADED=1` is the only way to watch a run on the real display.
- Vite `base: './'` in `vite.config.js` is required; Electron loads `dist/index.html` over `file://`, where absolute asset paths break.

## Architecture

Three-process Electron layout under `app/src/`:

- **`main/`**; Node/Electron main process.
  - `index.js` wires all IPC handlers and the daemon connect flow.
  - `herdr/client.js`; NDJSON unix-socket control-plane client (85-method API); `session.snapshot` bootstrap then `events.subscribe` with replay dedupe.
  - `herdr/streams.js`; pane stream supervisor: spawns one `herdr terminal session observe|control <pane>` child per visible pane, decodes base64 ANSI frames, and enforces **exclusive control: acquire on focus, release on blur**.
  - `providers/`; `history.js` runs the Node `history-index.js` worker (+ fs-watch on `~/.claude/projects`), `titles.js` runs the Node Haiku titler, `artifacts.js` discovers agent-produced files for the Artifacts view (see the views bullet below), `provider-history.js` scans the codex (`~/.codex/sessions`) and cursor (`~/.cursor/projects/*/agent-transcripts`) stores into rail rows of the same shape (title from the first user block the REAL TranscriptParser yields; cursor cwd un-munged from known cwds, honestly null when unmatched), `delegate.js` watches the claude-delegate queue, `usage.js` reuses the statusline method per account, `accounts.js` reads account emails, `capabilities.js` enumerates models/plugins/slash commands and owns the **new-session provider registry** (`newSessionOptions()`), and `model-catalog.js` keeps the Claude model list current by scanning the INSTALLED CLI binary (see gotchas).
  - `actions/launch.js` (resume/new) and `actions/orchestration.js` (kickoff + execute mutex) and `actions/takeover.js` (outside-session adoption). These shell out to `bin/` scripts and **never reimplement resume/index logic**.
  - `lifecycle.js`; daemon probe, clean-start, single-instance lock, and the protocol/schema compatibility assert.
  - `notify.js`; OS notifications on unfocused-pane work→idle transitions. `lag-monitor.js`, `sidebar-bridge.js`, `terminal-bridge.js` connect main↔renderer.
- **`preload/index.js`**; `contextBridge` exposes `window.harbor` (typed IPC only, no `nodeIntegration`). An extra `api.e2e` surface is gated on `HARBOR_E2E=1`.
- **`renderer/`**; React 19 (Slate): `sidebar/Sidebar` (the rail), `ViewSwitch.jsx` (the Agents/Orch/Artifacts toggle at the TOP of the rail, above Sessions and P/T/S; Pat placed it there 2026-07-25), `stage/Stage` + `stage/SessionTile` + `stage/Conversation` + `stage/CommandBar` (the conversation windows and universal prompt bar), `stage/ComposeEditor.jsx` + `stage/compose-doc.cjs` (the WYSIWYG contenteditable composer and its markdown serializer), `stage/md.jsx` (markdown-lite, React elements only; never injected HTML), `ContextMenu.jsx` (the app-wide right-click menu carrying spelling suggestions), `terminal/XtermPane` (the per-window `>_` raw-terminal mode), `TitleBar` (live pill + rail-toggle + `⚙ workers` chip; usage meters live in the rail only), `NewSessionConfig.jsx` (the new-session popover), `providers.js` (provider identity registry for logos/colors), `orchestration/OrchPanel` + `orchestration/OrchProjectPicker` (the top-level Orch view's project list), `artifacts/ArtifactsView.jsx` (the Artifacts view), `HelpOverlay`, `styles.css` (the Slate token sheet). Vite bundles this.
- **`shared/`**; logic used by both the renderer and the main/test side (see twin rule below).

Slate data plane (added 2026-07-18): `main/providers/transcript.js` tails and parses each open session's JSONL into conversation blocks (mass-tested against the full 1,400-file corpus); `main/session-send.js` is the command-bar engine; pane resolution, provisional session↔pane links (snapshot-diff discovery beats the 60-150s agent-detection lag), resume-then-send queueing with readiness polling, and honest failure statuses (`send:status` push). The **context gauge NEVER invents a denominator** (Pat mandate 2026-07-21, after the fifth wrong-percentage incident in four days, each one a guessed window: family defaults, assumed 1M, a table missing `claude-fable-5`). A percentage comes only from Claude's own math: the statusline tee at `~/.cache/harbor/context/<session>.json` (`used_percentage`, authoritative while fresh or while the transcript has not outgrown it), or a window LEARNED numerically from a pairable tee (`pct = tokens/window`, persisted to `<session>.learned.json`, clamped to [50k, 5M], survives restarts, re-learns on >10% drift so a mid-session model switch corrects within one statusline repaint). With neither, the chip and the `CTX` footer show the honest token count (`151k`), never a percent. There is NO per-model window table anywhere in the code; do not add one.

**Outside sessions adopt on send** (`session:takeover` → `window.harbor.session.takeover`): when a session is live outside Harbor (transcript hot, no Herdr pane), the command bar STAYS ENABLED and Enter moves the session into Harbor as part of the send: the adopt flow reads the statusline context tee at `~/.cache/harbor/context/<session>.json` for `{session_id, pid}`, verifies `/proc/<pid>/cmdline` is Claude, sends SIGTERM then SIGKILL if needed, resumes through `bin/claude-sessions --resume-id … --live-ok`, then delivers the composed text (and any image attachments). There is NO separate Take over button and no watch-only composer state (removed 2026-07-20: the two-click confirm dead-zoned natural click rhythms, and Pat vetoed the concept; the typed message IS the consent). An empty-composer Enter on an outside session is a no-op. **The readiness wait sizes the pane BEFORE it settles, and settles on MEANING not bytes (2026-07-28).** `waitForResumedClaudeReady` required two byte-identical reads 800ms apart, which was always luck (Claude's footer carries live cost/context numbers) and became impossible once panes get resized: a resize changes the wrap width and empties herdr's `recent` buffer, so a sizing landing mid-wait makes every read differ from the last. An adopt that times out there is the most expensive way for a message not to land, because adoption has ALREADY killed and resumed the session ("session adopted, but Claude never became ready"). The pane is now sized once, awaited, before the loop, and `settleKey` compares the screen with its trailing status lines dropped and whitespace collapsed. The adopt path also writes to the send log now (`sessionSend.logStatus`), because when it failed the only record anywhere was a truncated line in Pat's status bar. Missing or mismatched tee data still refuses honestly (`cannot identify the owning process` and kin) without resuming, but a VERIFIABLY GONE owner is not a dead end (live-caught 2026-07-24: the systemd-oomd kill of the daemon's terminal scope left a working-tailed transcript and a dead tee pid, and the first Enter refused): a dead pid, a recycled pid whose cmdline is no longer claude, or a zombie (empty cmdline) falls through to resume-then-send after a best-effort `/proc` scan confirms no other live claude carries the session id; a scan hit refuses honestly and retryably, and the scan NEVER picks a kill target, signals stay strictly tee-verified. The renderer side of the same incident family lives in the `session-liveness` shared twins: `processAlive: false` (exact, pid-reuse-guarded, computed at emit time) outranks a stale `working` flag, because a session killed mid-turn freezes its transcript in a working state; status pushes on `send:status`. Adopting a session mid-turn kills its in-flight turn; adopting an autonomous loop session ends that loop's process and continues the conversation in Harbor.

## Non-obvious conventions and gotchas

- **Product code never spawns Python (2026-08-04).** The 2026-08-03 incident proved that timeouts, a slot cap, a wedge breaker and a canary can only bound a kernel-wedged interpreter; they cannot make it safe. `history-index.js` now owns indexing, `titles.js` owns Haiku titles, and `harbor-bin.cjs` uses the same Node index for the daily `hist` picker and workspace labels. `reference/python-oracles/` is test data for byte-equivalence only. A production `python3`, `.py` spawn, or `sharedPythonRunner` reference is a release blocker. `createSessionOwnerProbe` still carries a 3s deadline on both of its `/proc` questions, and `PaneStreamSupervisor._wire` still listens for stdin EPIPE, because those independent incident guards remain necessary.
- **`.js` / `.cjs` twins in `src/shared/`.** Every shared module ships as both an ESM `.js` (imported by the renderer JSX) and a CommonJS `.cjs` (required by the main process and the Node test runner): `sidebar-model`, `date-roll`, `terminal-layout`. **Edit both twins together and keep them identical**; drift silently breaks either the UI or the tests. Tests import the `.cjs` variant.
- **Never start the Herdr daemon except via `bin/herdr-server-clean`.** A daemon started from inside a Claude session leaks that session's ids/API keys into every pane it spawns (`herdr-server-clean` uses an `env -i` allowlist). The app auto-starts through it; scripts and harnesses must too. It is also the ONE sanctioned recovery for a **wedged daemon** (live-caught 2026-07-17 and 2026-07-21: main thread dies silently, worker threads keep the listening socket, so the socket ACCEPTS connections into a dead queue and every untimed herdr client hangs forever while `probeSocket` reports healthy): it decides liveness with a REAL request, moves the non-answering `herdr.sock`/`herdr-client.sock` aside as `*.dead-<ts>` (never deleted), and moves `session.json` aside too, because a fresh daemon would otherwise auto-resume every restored agent pane (`resume_agents_on_restore` defaults on) while the orphaned original claude processes may still hold those session ids (double-writers on one transcript). Never kill the zombie daemon's surviving threads while orphaned panes hold live claude processes; leave them as outside sessions and let adopt-on-send claim them. Every herdr CLI call in `bin/ai` / `bin/claude-sessions` is `timeout`-wrapped so a wedge fails fast and honestly (the 2026-07-21 eternal "Working..." dialog), and `connectDaemon` retries once through `herdr-server-clean` when a connect succeeds but `session.snapshot` times out (an app restart can never fix a daemon-side wedge). A wedge mid-session is silent (established connections stay open, `connection-lost` never fires), so `main/daemon-watchdog.js` pings every 30s and on two consecutive failures recovers the daemon and relaunches the app onto it (rail/stage/drafts persist; disabled under `HARBOR_E2E`/`HARBOR_NO_DAEMON_START`). **A timeout guards a probe that HANGS; it does nothing about a probe that LIES, and liveness therefore lives in ONE place: `bin/herdr-health.sh` (2026-07-26).** Live-caught by Pat with Harbor unusable behind a "Reconnecting..." banner while every documented layer above ran correctly: the watchdog tripped, `connectDaemon` called `herdr-server-clean`, the script exited 0, and nothing was recovered, every 60 seconds for eight minutes. The wedge that day left the thread-group leader as a `Zsl` zombie, and a zombie daemon still answers `herdr status` with `status: running` in milliseconds, because that reply is served without the main thread, while `session.snapshot`, `workspace list`, `pane list` and `agent list` all hang. So `herdr-server-clean`'s OPENING gate ("already running, leave it") believed it and returned before reaching the move-aside recovery ten lines below, which is why the forensic trail showed no new `*.dead-<ts>` and no new `=== herdr server start ===` on the day of an eight-minute outage. `herdr_daemon_healthy` is now the only answer to "is the daemon usable": a timed `herdr api snapshot`, deliberately the CLI form of the `session.snapshot` the app itself depends on, so the probe and the app can never drift on what "up" means (healthy exits 0 at once, a wedge hangs into the timeout, no daemon fails in ~0.1s). FOUR scripts shared the lying gate and all four now source the helper: `herdr-server-clean` (the outage), `bin/ai` and `bin/claude-sessions` (whose comments claimed routing a failed status probe through recovery "heals both the dead and the wedged case", which was false precisely for the wedge), and `bin/harbor-hydrate`, the worst of them, because every herdr call below its gate is UNTIMED and it sailed past into an eternal hang. `started clean` now also means the fresh daemon ANSWERED A REAL REQUEST rather than reported running, on a bounded deadline (`HARBOR_HERDR_READY_TIMEOUT`), since the caller's very next act is a real request and a premature success only relocates the failure. Never decide herdr liveness from a reply the daemon can produce while its main thread is dead. The fixture is the other half of the lesson: the suite had modelled a wedge as `herdr status` HANGING (which the timed probe cut through, so cases 1-4 passed for years while the real shape walked past them), and spec 5/6 are two-sided ON PURPOSE, a lying wedge must still be recovered AND a daemon that answers must still be left alone, or every launcher would bounce a healthy daemon out from under Pat's live panes. **The daemon runs in its OWN systemd unit, not the cgroup of the window that started it (2026-07-28).** `setsid nohup` detaches from the process TREE but not from the CGROUP, so the daemon, every pane it forked and every claude in them inherited `app-gnome-harbor-<pid>.scope`, the scope gnome-shell created for that Harbor launch (measured that morning at 584 tasks in one scope with the daemon inside it). Two consequences, both live-caught: one OOM or oomd kill on that scope takes the daemon, every pane and every live session with it (2026-07-24, and again 2026-07-28 06:18 with the swapfile 100% full), and a second Harbor launch grows a SECOND daemon in a second scope, which is how two herdr daemons ran at once with one of them still holding 172 processes from three days earlier. `herdr-server-clean` now starts it with `systemd-run --user --unit=herdr-daemon --collect`, keeping the SAME `env -i` allowlist (passed as `--setenv`, because a daemon started with a session's environment leaks that session's ids into every pane it spawns). One stable name also means a second daemon cannot hide. `HERDR_NO_SYSTEMD_UNIT=1` or a missing `systemd-run` falls back to the old `setsid` path, so the worst case is today's behaviour; `HARBOR_HERDR_UNIT` renames the unit for harnesses. **A UNIT NAME IS A SHARED NAMESPACE, and the harness does not get to forget it (2026-07-29).** The very suite that proves this recovery, `app/test/bin/herdr-wedge-recovery.test.js`, isolated the herdr binary, the config dir, the log and the timeouts but not the unit NAME, so `startClean` resolved the default and ran `systemctl --user stop herdr-daemon` against Pat's LIVE daemon, which kills that unit's whole cgroup: the daemon, every pane it forked and every claude session in them. Harbor's watchdog then recovered behind it, so what he saw was a yellow reconnecting banner and dead sessions, eight times in twenty-two minutes, once per `npm test`; the journal shows `Stopping ... /home/you/.local/bin/herdr server` immediately followed by `Started ... /tmp/harbor-wedge-test-0WUGYn/herdr server`, and `/tmp` held 160 stub dirs. The suite's own spec ASSERTED `--unit=herdr-daemon` from a relocated harness, so the bug was a gate-defended requirement, green throughout. The floor is therefore `resolveUnitPolicy` in `/home/you/dev/harbor/bin/harbor-bin.cjs`, a fourth sibling of the signal, launch and dialog policies rather than a line of env in each harness: a run that relocated `HARBOR_HERDR_BIN` or `HARBOR_HERDR_DIR` is by definition not the real installation, so the default unit is not its unit to stop, and it drops to the detached spawn (exactly what `HERDR_NO_SYSTEMD_UNIT=1` does, so the worst case is the pre-2026-07-28 behaviour). Naming a unit is the escape and the harness picks the name. The proof is two-sided ON PURPOSE, because a refusal alone passes just as well if the systemd path were dead everywhere: a relocated harness must reach systemd NOT AT ALL, and a harness that names its own unit must still get `--unit=<its name>` with the `--setenv` clean-env allowlist intact. The suite also carries recording `systemctl`/`systemd-run` stubs on its stub PATH now, so it cannot reach the real user manager even if the guard is bypassed. Never assert a production-default resource NAME from a harness that is pointed at a stub. It takes effect at the next daemon lifecycle, never by restarting a daemon that is holding live panes. Daemon stderr appends to `~/.cache/harbor/herdr-daemon.log`, never `/dev/null`, so the next silent death leaves a panic trace. Tests: `app/test/bin/herdr-wedge-recovery.test.js`, `app/test/main/daemon-watchdog.test.js`.
- **Tests must never touch the real user daemon.** Use the isolated named-session harness (`test/herdr/harness.js`). `HARBOR_NO_DAEMON_START=1` skips clean-start; set `HERDR_SOCKET_PATH` to point main-process code at an isolated socket. - **The whole window is one drop zone, and NOTHING dropped may navigate (2026-07-25).** Harbor had no drop handling at all, so a dropped file hit Chromium's default and navigated the renderer at it, replacing the app (rail, stage and every open window) with the file: that is the window Pat lost. `renderer/use-file-drop.js` claims any drag whose `dataTransfer.types` includes `Files`, in CAPTURE phase on `window`, so no child can swallow one and leave the default in place (xterm pastes dropped paths itself); `main/index.js` independently refuses `will-navigate` and denies `setWindowOpenHandler`, because this app never navigates after its own load. Both layers stand whether or not the drop is handled. A dropped IMAGE takes the paste path (bytes saved through `clipboard:save-image`, attached with a thumbnail), so nothing depends on resolving its original path; any OTHER file takes the `+ add files` path (absolute path appended to the draft text) and needs `webUtils.getPathForFile` from the PRELOAD, since a `File` has carried no `path` since Electron 32 (`window.harbor.files.pathFor`, `''` when the OS did not supply one, reported honestly rather than invented). The drop writes to the SELECTED session's draft read at drop time by id, never a stale closure, and with no session selected it refuses in the overlay instead of silently eating the file. Decisions live in `renderer/stage/file-drop.cjs` so the overlay, the handler and the tests cannot drift.

- **Worker close verifies the PROCESS died, not just the pane.** `closePaneTab` captures the pane's pid (via `processInfo`) BEFORE closing, because a clean tab-close removes the pane from the daemon while its `claude --resume` process (and its stdio MCP children) can survive the pty teardown. Pane-absence alone is a HALF kill; when the captured pid outlives the close, it escalates to an exact SIGTERM/SIGKILL on the process group and re-verifies, so `verified: true` always means the process is gone. The `+signal` method suffix records that escalation ran.
- **Out-of-band restarts never steal the screen, and the FLAG IS NOT THE GUARANTEE (2026-07-27, interrupted a full-screen game).** `--no-focus-steal` was passed on every relaunch that day and Harbor still came up over the game; X said so plainly afterwards, `_NET_ACTIVE_WINDOW` was Harbor and `_NET_CLIENT_LIST_STACKING` put Harbor above the game. Two paths did it. **Order**: `showInactive()` was followed by `window.maximize()`, and asking mutter to maximize an ALREADY-MAPPED window activates it; maximizing while still hidden shows it unfocused instead (Electron's own documented behaviour), so the maximize now happens FIRST. **The single-instance handler**: a relaunch racing a not-yet-dead instance lands in `second-instance`, which called `mainWindow.focus()` unconditionally; `parseSecondInstanceArgs` now carries `noFocusSteal` through so that path honours it too. On top of both, `main/focus-guard.js` CHECKS THE OUTCOME instead of trusting the hint: it records `_NET_ACTIVE_WINDOW` before showing and, for ~1.5s after, hands the screen straight back (`wmctrl -i -a <previous>`) if X says we became active. Activating the previous window is what restacks it above ours, which is the actual requirement: an unfocused window still COVERS a full-screen game, so focus alone was never the ask. Every part degrades to a no-op without X/tools, and a launch that was already the active window is left alone so Pat's own clicks are never fought. ANY scripted/agent restart still passes the flag (`/home/you/.local/bin/harbor --no-focus-steal`), and must then VERIFY from X that Harbor is neither the active window nor above the game, because that verification is the step whose absence let this ship. This replaces the accidental protection the game's always-on-top focus-denial used to provide (removed by the 2026-07-15 toast fix; live-caught 2026-07-24, then again worse on 2026-07-27).
