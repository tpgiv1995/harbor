# CLAUDE.md archive: the Linux/Herdr era (retired 2026-08-10 and 2026-08-14)

This file preserves the CLAUDE.md sections that described mechanisms which no longer exist: the Herdr backend (retired 2026-08-14, sessiond is the only backend) and the Linux desktop install (retired 2026-08-10). The incidents were real and the principles they taught are carried forward in the current CLAUDE.md (liveness is a real request never a status reply; fail-closed allowlists; a relocated harness touches nothing real; a unit or resource name is a shared namespace); only the mechanisms below are dead.

## The old headline: Herdr as the backend

Harbor was an Electron GUI head on a stock, pinned Herdr 0.7.4 daemon; the GUI never forked or replaced Herdr; it drove Herdr's third-party client surface (`session.snapshot`, `events.subscribe`, and the `herdr terminal session observe|control` byte bridge) for pty control, while conversations rendered from transcripts. `main/herdr/client.js` was an NDJSON unix-socket control-plane client (85-method API): `session.snapshot` bootstrap then `events.subscribe` with replay dedupe. `main/herdr/streams.js` was the pane stream supervisor: one `herdr terminal session observe|control <pane>` child per visible pane, decoding base64 ANSI frames, enforcing exclusive control (acquire on focus, release on blur). Both files, the whole `app/test/herdr/` suite, `bin/herdr-server-clean`, `bin/herdr-health.sh`, `bin/harbor-hydrate`, `docs/UPSTREAM-HERDR.md`, and `docs/herdr-api.schema.json` were deleted in the 2026-08-14 retirement series. `docs/ARCHITECTURE-v2.md` remains as the historical daemon-plumbing record, superseded by `docs/SESSION-DAEMON-CUTOVER.md`.

## The wedge recovery saga (herdr-server-clean)

Never start the Herdr daemon except via `bin/herdr-server-clean`. A daemon started from inside a Claude session leaks that session's ids/API keys into every pane it spawns (`herdr-server-clean` used an `env -i` allowlist). The app auto-started through it; scripts and harnesses had to too. It was also the ONE sanctioned recovery for a wedged daemon (live-caught 2026-07-17 and 2026-07-21: main thread dies silently, worker threads keep the listening socket, so the socket ACCEPTS connections into a dead queue and every untimed herdr client hangs forever while `probeSocket` reports healthy): it decided liveness with a REAL request, moved the non-answering `herdr.sock`/`herdr-client.sock` aside as `*.dead-<ts>` (never deleted), and moved `session.json` aside too, because a fresh daemon would otherwise auto-resume every restored agent pane (`resume_agents_on_restore` defaults on) while the orphaned original claude processes may still hold those session ids (double-writers on one transcript). Never kill the zombie daemon's surviving threads while orphaned panes hold live claude processes; leave them as outside sessions and let adopt-on-send claim them. Every herdr CLI call in `bin/ai` / `bin/claude-sessions` was `timeout`-wrapped so a wedge failed fast and honestly (the 2026-07-21 eternal "Working..." dialog), and `connectDaemon` retried once through `herdr-server-clean` when a connect succeeded but `session.snapshot` timed out (an app restart can never fix a daemon-side wedge). A wedge mid-session is silent (established connections stay open, `connection-lost` never fires), so `main/daemon-watchdog.js` pinged every 30s and on two consecutive failures recovered the daemon and relaunched the app onto it.

**A timeout guards a probe that HANGS; it does nothing about a probe that LIES, and liveness therefore lived in ONE place: `bin/herdr-health.sh` (2026-07-26).** Live-caught by Pat with Harbor unusable behind a "Reconnecting..." banner while every documented layer above ran correctly: the watchdog tripped, `connectDaemon` called `herdr-server-clean`, the script exited 0, and nothing was recovered, every 60 seconds for eight minutes. The wedge that day left the thread-group leader as a `Zsl` zombie, and a zombie daemon still answers `herdr status` with `status: running` in milliseconds, because that reply is served without the main thread, while `session.snapshot`, `workspace list`, `pane list` and `agent list` all hang. So `herdr-server-clean`'s OPENING gate ("already running, leave it") believed it and returned before reaching the move-aside recovery ten lines below, which is why the forensic trail showed no new `*.dead-<ts>` and no new `=== herdr server start ===` on the day of an eight-minute outage. `herdr_daemon_healthy` became the only answer to "is the daemon usable": a timed `herdr api snapshot`, deliberately the CLI form of the `session.snapshot` the app itself depends on, so the probe and the app can never drift on what "up" means (healthy exits 0 at once, a wedge hangs into the timeout, no daemon fails in ~0.1s). FOUR scripts shared the lying gate and all four were fixed to source the helper: `herdr-server-clean` (the outage), `bin/ai` and `bin/claude-sessions` (whose comments claimed routing a failed status probe through recovery "heals both the dead and the wedged case", which was false precisely for the wedge), and `bin/harbor-hydrate`, the worst of them, because every herdr call below its gate was UNTIMED and it sailed past into an eternal hang. `started clean` also came to mean the fresh daemon ANSWERED A REAL REQUEST rather than reported running, on a bounded deadline (`HARBOR_HERDR_READY_TIMEOUT`), since the caller's very next act is a real request and a premature success only relocates the failure. Never decide daemon liveness from a reply the daemon can produce while its main thread is dead. The fixture was the other half of the lesson: the suite had modelled a wedge as `herdr status` HANGING (which the timed probe cut through, so cases 1-4 passed for years while the real shape walked past them), and spec 5/6 were two-sided ON PURPOSE: a lying wedge must still be recovered AND a daemon that answers must still be left alone, or every launcher would bounce a healthy daemon out from under Pat's live panes.

## The systemd unit doctrine

**The daemon ran in its OWN systemd unit, not the cgroup of the window that started it (2026-07-28).** `setsid nohup` detaches from the process TREE but not from the CGROUP, so the daemon, every pane it forked and every claude in them inherited `app-gnome-harbor-<pid>.scope`, the scope gnome-shell created for that Harbor launch (measured that morning at 584 tasks in one scope with the daemon inside it). Two consequences, both live-caught: one OOM or oomd kill on that scope takes the daemon, every pane and every live session with it (2026-07-24, and again 2026-07-28 06:18 with the swapfile 100% full), and a second Harbor launch grows a SECOND daemon in a second scope, which is how two herdr daemons ran at once with one of them still holding 172 processes from three days earlier. `herdr-server-clean` started it with `systemd-run --user --unit=herdr-daemon --collect`, keeping the SAME `env -i` allowlist (passed as `--setenv`, because a daemon started with a session's environment leaks that session's ids into every pane it spawns). One stable name also means a second daemon cannot hide. `HERDR_NO_SYSTEMD_UNIT=1` or a missing `systemd-run` fell back to the old `setsid` path; `HARBOR_HERDR_UNIT` renamed the unit for harnesses.

**A UNIT NAME IS A SHARED NAMESPACE, and the harness does not get to forget it (2026-07-29).** The very suite that proved this recovery, `app/test/bin/herdr-wedge-recovery.test.js`, isolated the herdr binary, the config dir, the log and the timeouts but not the unit NAME, so `startClean` resolved the default and ran `systemctl --user stop herdr-daemon` against Pat's LIVE daemon, which kills that unit's whole cgroup: the daemon, every pane it forked and every claude session in them. Harbor's watchdog then recovered behind it, so what he saw was a yellow reconnecting banner and dead sessions, eight times in twenty-two minutes, once per `npm test`; the journal shows `Stopping ... /home/you/.local/bin/herdr server` immediately followed by `Started ... /tmp/harbor-wedge-test-0WUGYn/herdr server`, and `/tmp` held 160 stub dirs. The suite's own spec ASSERTED `--unit=herdr-daemon` from a relocated harness, so the bug was a gate-defended requirement, green throughout. The floor became `resolveUnitPolicy` in `bin/harbor-bin.cjs`: a run that relocated `HARBOR_HERDR_BIN` or `HARBOR_HERDR_DIR` is by definition not the real installation, so the default unit is not its unit to stop, and it drops to the detached spawn. Naming a unit is the escape and the harness picks the name. The proof was two-sided ON PURPOSE, because a refusal alone passes just as well if the systemd path were dead everywhere: a relocated harness must reach systemd NOT AT ALL, and a harness that names its own unit must still get `--unit=<its name>` with the `--setenv` clean-env allowlist intact. The suite also carried recording `systemctl`/`systemd-run` stubs on its stub PATH, so it could not reach the real user manager even if the guard were bypassed. Never assert a production-default resource NAME from a harness that is pointed at a stub. (`resolveUnitPolicy` is still live code in `bin/harbor-bin.cjs`; the sessiond store isolation rule imports it, which is why the retirement kept it.) Daemon stderr appended to `~/.cache/harbor/herdr-daemon.log`, never `/dev/null`, so the next silent death leaves a panic trace.

## The protocol allowlist

Herdr was pinned to 0.7.4. Never call `herdr update` from code/automation. On connect the app asserted the daemon protocol against an ALLOWLIST, `SUPPORTED_PROTOCOLS = [16, 17]`, with schema_version 1; anything else showed the degraded-daemon banner rather than misbehaving. It was deliberately an allowlist and not a `>=` comparison, so a future protocol fails closed and gets read by a human instead of being accepted for having a bigger number. 16 was 0.7.4, the pinned stable build Linux ran. 17 was added on 2026-07-29 because Herdr published Windows binaries ONLY on the preview channel, so no Windows build spoke 16 and Harbor could not connect to a Windows daemon at all (a Windows box installed `0.7.5-preview.2026-07-21-0f10e1453a7f` and reported `"protocol":17` from a real `herdr api snapshot`, and Harbor's own `assertDaemonCompat` answered `protocol_mismatch: expected 16, got 17`). Widening it was CHECKED, not assumed: `herdr api schema --json` from each daemon, diffed, gave a whole delta of one method removed (`agent.send`) and five added (`agent.prompt`, `agent.send_keys`, `agent.view.clear`, `agent.view.set`, `agent.wait`). Harbor called none of them, and all 49 herdr names referenced in `main/herdr/client.js` were verified present in the protocol 17 schema, with `schema_version` 1 in both. Never widen a compatibility check by comparison operator, and never add a protocol without diffing the schemas first. The fail-closed-allowlist principle survives the backend.

## The xvfb/dbus e2e gate

`npm run test:e2e` was a two-run gate: both consecutive Playwright runs must be green or it fails. It (and `scripts/verify-all.js` / `scripts/verify-chrome.js`) ALWAYS ran under `xvfb-run` with the session displays scrubbed; test windows must never open on the live desktop and steal focus. `HARBOR_E2E_HEADED=1` was the only way to watch a run on the real display.

**A harness cannot open a native file dialog, and the SESSION BUS is the third thing xvfb does not isolate (2026-07-26).** Live-caught by Pat after ninety minutes of a GNOME file chooser stealing focus on his real desktop every few minutes while the gate ran. Electron does NOT draw `dialog.showOpenDialog` itself: it calls `org.freedesktop.portal.FileChooser` over the session bus, where `xdg-desktop-portal-gnome` activates Nautilus and draws it on the LIVE session. `env -u DISPLAY -u WAYLAND_DISPLAY xvfb-run` isolates X11 and nothing else, so `DBUS_SESSION_BUS_ADDRESS` is untouched and the picker walks straight out of the harness; the same shape as the 2026-07-25 self-kill, where socket, profile and display were isolated but `$HOME` was not. **Isolating the parts you thought of is not isolation.** It is also not merely noisy: `showOpenDialog` is MODAL and awaits an answer no test can give, so it BLOCKS the main process while it sits there, which is what an unexplained "only fails on run 2 of the two-run gate" looks like. `scripts/e2e.js` became the fence: the suite ran under `dbus-run-session` with its own bus AND cleared `DBUS_SESSION_BUS_ADDRESS`, so anything portal-backed added later (notifications, screenshots) also could not reach the real desktop. The `resolveDialogPolicy` floor this incident produced is still live and platform-neutral; only the portal/session-bus plumbing described here is Linux.

## One session is one cgroup (the Linux containment story, 2026-08-09)

Every keeper used to fork into the daemon's own cgroup, so at 00:28 systemd-oomd killed `harbor-sessiond.service` whole: 20 sessions, 497 processes, 45.7G, with the desktop already paged out (Pat experienced "machine bricked, RuneLite crashed"; RuneLite was fine). At 02:15 the Claude CLI's own bundled grep (a backgrounded Bash-tool child of one session, comm `2.1.226`) grew unboundedly on a single-line HTML file in that same shared cgroup: 36.4G RSS, swap 100%, memory PSI 86%, and every layer above told the truth slowly. The containment half of the fix: `src/daemon/session-scope.js`, every session spawned via `systemd-run --scope` as `harbor-session-<id>.scope` under `harbor-sessions.slice` (per-session MemoryHigh=8G/MemoryMax=12G; the slice ceiling DERIVED from RAM with at least a third reserved for the desktop, self-installed unit file, idempotent; a relocated store gets no scopes unless it names its own slice, the `resolveUnitPolicy` rule one layer down; scope unusable falls back to the shared-cgroup behaviour, because losing containment beats refusing to open sessions). Proven live: a memcg kill named the one scope, the neighbour session and the desktop stayed untouched, PSI recovered within seconds. The keeper also raised its pty child's `oom_score_adj` to 500 (inherited on fork, so a runaway grandchild carries it), making the kernel prefer session processes over the keeper, which survives to record an honest exit; the containment proof caught the kernel choosing the KEEPER without this. `memory.high` throttling means a runaway CRAWLS from High to Max under heavy reclaim stall attributed to its own scope, which is precisely the pressure signature oomd needs to pick that one scope if the kernel wall is never reached. Operational facts proven during the live cutover: `bin/harbor-sessiond start` set `KillMode=process`, so a daemon stop touched ONLY the daemon and running keepers survived it (done twice with a live session); pre-scope keepers were migrated into scopes without signaling anything via the user manager's `StartTransientUnit` PIDs adoption. Verify any containment change from the kernel (`memory.max` readback, a real memcg kill naming the scope), never from systemctl output alone. On the Windows install `session-scope.js` reports `not linux` and containment is honestly disabled; the platform-neutral guards from the same incident (spawn reap, keeper socket error listener, periodic reconcile) remain in the current CLAUDE.md.

## The X11 focus guard

**Out-of-band restarts never steal the screen, and the FLAG IS NOT THE GUARANTEE (2026-07-27, interrupted a full-screen game).** `--no-focus-steal` was passed on every relaunch that day and Harbor still came up over the game; X said so plainly afterwards, `_NET_ACTIVE_WINDOW` was Harbor and `_NET_CLIENT_LIST_STACKING` put Harbor above the game. Two paths did it. **Order**: `showInactive()` was followed by `window.maximize()`, and asking mutter to maximize an ALREADY-MAPPED window activates it; maximizing while still hidden shows it unfocused instead (Electron's own documented behaviour), so the maximize now happens FIRST. **The single-instance handler**: a relaunch racing a not-yet-dead instance lands in `second-instance`, which called `mainWindow.focus()` unconditionally; `parseSecondInstanceArgs` carries `noFocusSteal` through so that path honours it too. On top of both, `main/focus-guard.js` CHECKED THE OUTCOME instead of trusting the hint: it recorded `_NET_ACTIVE_WINDOW` before showing and, for ~1.5s after, handed the screen straight back (`wmctrl -i -a <previous>`) if X said we became active. Activating the previous window is what restacks it above ours, which is the actual requirement: an unfocused window still COVERS a full-screen game, so focus alone was never the ask. Every part degrades to a no-op without X/tools, which is exactly what happens on win32: there is NO focus guard on Windows, and the current CLAUDE.md states the rule that replaces it (never restack or focus windows from automation, period).

## keyd

Copilot-key / keyd changes applied via `/usr/bin/keyd reload` only; never `systemctl restart keyd` on the live desktop (a restart once killed every open terminal). keyd does not exist on Windows.
