- **The Board view is an Excalidraw whiteboard that works with the network unplugged (2026-08-25, task t_mt8z04r36a96d2x).** Pat wanted a Miro-shaped infinite canvas for visual Q&A (his reference board: columns of pasted screenshots annotated with sticky notes). `@excalidraw/excalidraw` (MIT; tldraw was ruled out on its production license key + watermark) renders in `renderer/whiteboard/WhiteboardView.jsx`, lazy-loaded so the Agents stage never pays its chunk on boot. **Nothing fetches a CDN**: fonts are copied from the package into `public/excalidraw-assets/` by a `buildStart` step in `vite.config.js` (the copy is gitignored) and `window.EXCALIDRAW_ASSET_PATH` is set in `index.html` BEFORE the module loads. **It MUST be an ABSOLUTE url (`new URL('./excalidraw-assets/', document.baseURI).href`), and a relative `'./excalidraw-assets/'` was the original spelling that silently broke offline the moment any TEXT landed on a board (2026-08-26)**: Excalidraw resolves CONTENT-font urls (Excalifont and kin) with `new URL(path, base)` where `normalizeBaseUrl` resolves a relative base against `location.origin`, which under file:// is the drive ROOT (or the string `"null"`), so the local font 404'd and Excalidraw fell through to its `esm.sh` CDN fallback. CSS-based UI fonts resolve relative to the document so they were fine, which is why only the hand-drawn content font leaked, and ONLY once text was rendered/exported. The shape-only drive never put text on a board, so the hole hid for the feature's whole first day until the sticky/template toolbar made text one click. The drive (`scripts/drive-whiteboard-win.js`, port 9338) records every CDP network request and asserts zero http/https, and now drops a sticky note, a flowchart, and a Copy-PNG export so fonts are actually exercised. Boards persist as JSON files (`HARBOR_BOARDS_DIR` then `paths.boardsDir` then `<userData>/boards`) through `main/providers/whiteboard.js`: atomic tmp+rename with `.bak`, corrupt files quarantined never overwritten, and **delete moves to a `.trash` subfolder rather than unlinking, because a whiteboard is user work**; saves debounce ~1.2s and flush on view switch. Pasted screenshots ride the scene JSON as embedded files and survive an app restart (drive-proven). The whole-window drop capture exempts `.excalidraw` targets so an image dropped on the canvas reaches Excalidraw's own handler; the never-navigate default stands everywhere else. **The Miro-parity sweep and the latency fix (2026-08-26)** answer Pat's "it works but kinda sucks": the canvas was serializing the ENTIRE scene (`serializeAsJSON`+`JSON.parse`, megabytes with an embedded screenshot) on EVERY `onChange`, which Excalidraw fires on every pointer move, so a drag stringified the whole board 60x/second. `WhiteboardCanvas.jsx` now stores the raw refs on change and serializes ONCE inside a version-gated debounced flush (`getSceneVersion` + a persisted-appState fingerprint via `board-files.cjs` `boardChanged`, so a bare pan/zoom never writes), which is the whole fix; `WhiteboardView` re-renders no longer touch the canvas (it is `React.memo`, and `restore()` is memoized). A floating bottom-center toolbar (`.wb-toolbar`) adds one-click **sticky notes** in six colors (a clean rounded rect dropped at the viewport center via `convertToExcalidrawElements`, keyboard `N`, double-click to type the way Excalidraw binds text natively), one-click **templates** (Kanban / 2×2 matrix / flowchart with id-bound arrows / mind map, all pure skeleton builders in `board-files.cjs`), **grid** and **snap** toggles, and **Copy PNG** (`exportToBlob` to the clipboard through the new LOCAL_ONLY `clipboard:write-image` IPC, so a board pastes straight into Teams/Outlook). The Excalidraw `MainMenu` is customized to DROP its `Socials`/`LiveCollaborationTrigger` promo (Excalidraw+ / sign-up / live-collab), and a Harbor-branded `WelcomeScreen` greets an empty board. All of it drive-verified against a real canvas (sticky lands centered, every flowchart arrow binds, grid writes appState, Copy PNG round-trips, http=0). **The Miro-fidelity pass (2026-08-26) makes Excalidraw the engine and the chrome ours, on a LIGHT board.** The colour bug Pat hit (a black border rendered white, a `#f6d9ae` sticky rendered `#462d08`) was Excalidraw's DARK theme: it renders the canvas in light-mode colours then INVERTS the whole canvas for display (`.theme--dark canvas { filter: invert(93%) hue-rotate(180deg) }`), so every literal colour flips. A dark canvas with literal, export-correct colours is not achievable in Excalidraw (the filter is load-bearing for grid/text/default-stroke on dark), so the board runs **`theme="light"`** (WYSIWYG colours, dark text, correct export) with `.excalidraw canvas { filter: none !important }` as insurance and ToggleTheme removed from the menu. New content defaults to clean edges (`currentItemRoughness: 0`), solid fill, and the **Nunito** sans (`FONT_FAMILY.Nunito`, forced onto skeleton labels too) instead of the hand-drawn look; the ITEM_DEFAULTS WIN over the board's saved appState (a board saved with Excalidraw's sketchy roughness was dragging new shapes back to janky, live-caught 2026-08-26) and **existing elements are normalized to `roughness: 0` at load** so a board full of old sketchy shapes reads clean; stickies are flat and BORDERLESS (`strokeColor: 'transparent'`) with medium-saturated fills; the template palette is light-canvas pastels with dark labels. The native chrome is hidden (`.App-toolbar-container`, `.App-menu__left`) and replaced: a vertical **tool rail** (`.wb-rail`) drives `setActiveTool`; the sticky tool DROPS a sticky on a single click (default yellow) and reveals its colour palette on HOVER (a flyout requiring a second click was a regression Pat caught: clicking the tool must add a sticky, not open a menu), the shapes (rectangle/ellipse/diamond) and templates are click-flyouts, plus grid/snap at the bottom; the rich 15-colour **style bar** floats bottom-centre ONLY on selection (`recolorElements`/`setSelectionProp`/`selectionStyle` in `board-files.cjs`, fill vs line + stroke width, applied via `updateScene`); Copy PNG moved to the main menu; the top board-picker header is slimmed. **Right-drag pans** the canvas Miro-style (writes scrollX/scrollY with `CaptureUpdateAction.NEVER`, a plain right-click still menus). **Connectors** (`ConnectorLayer`, portalled to body): a single selected connectable shape shows four edge dots; dragging from a dot onto another shape creates an arrow bound to BOTH via manual `startBinding`/`endBinding` + mirrored `boundElements` (convertToExcalidrawElements only binds within its own batch), starting/ending at the shape edges (`boxEdgePoint`). (5) A **connector style bar** appears when the selection is only connectors (mutually exclusive with the shape fill/line bar via `selectionIsConnector`): routing Straight/Curved/Elbow, line style Solid/Dashed/Dotted, arrowheads end/both/start/none, plus colour and width. **Routing is done by REWRITING the connector's own `points`** (`routeConnector` in `board-files.cjs`: 2-point straight, an L of right angles for elbow, a bowed midpoint + `roundness:{type:2}` for curved) because Excalidraw's `elbowed` flag alone is INERT on an existing arrow (verified live: flipping it left the old points, so the line stayed straight); `strokeStyle` and start/`endArrowhead` DO apply directly. Drive spec 17 selects the drive's bound connector and asserts elbow adds waypoints, curved is 3 points with roundness 2, dashed applies, both-ends arrowheads apply, and that hovering an unselected shape shows 4 dots that retract on move-off; `board-files.test.js` unit-tests the pure connector helpers. **The sticky drop-shadow, which IS achievable (2026-08-26, "theirs look better and like actual sticky notes"):** Excalidraw has no per-element shadow, but a real Miro sticky is a flat coloured square LIFTED by a soft drop shadow, so a sticky is now TWO elements: a low-opacity dark square (`STICKY_SHADOW_*` in `board-files.cjs`, opacity 13, offset +5/+7) behind the coloured face. It is NOT grouped: grouping made Excalidraw demand you enter the group before double-click-to-type worked (drive-caught: the label gesture broke). Instead the shadow is `locked: true` (non-interactive, never independently selectable) and carries `customData: { stickyShadow: true, faceId }`; `syncStickyShadows` (called from `handleChange`, deferred one frame via rAF and coalesced so a drag schedules at most one sync/frame, never re-entering updateScene) glues the shadow to its face's position/size and removes an orphaned shadow when its face is deleted. **That orphan cleanup took two live bugs to get right (2026-08-26, "deleting a sticky left the shadow, you separated the layers"):** `onChange` hands the FULL element list INCLUDING the just-deleted face marked `isDeleted:true`, so "face missing from the list" never fired: a present-but-`isDeleted` face must also count as gone. And Excalidraw's `updateScene` MERGES by id, so omitting the orphan from the array leaves it on the board; the shadow must be MARKED `isDeleted:true` to actually go. Both are asserted by a REAL Delete of a placed sticky leaving zero orphan shadows. The face stays a normal single element, so click, double-click-to-type, single-selection connectors, and recolour (which skips `isStickyShadow`) all work; `elementAtClient` and the selected-connect-dot resolver skip shadows so a sticky's face, not its shadow, is the connect target. Corners stay sharp (Excalidraw's adaptive rounding reads as a button). **The connect dots no longer LAG a dragged shape (2026-08-26, Pat's screenshot of dots stranded behind a moved sticky):** the rendered anchor is `hoverAnchor || connectAnchor`, and a drag freezes `hoverAnchor` (the hover recompute bails while a button is held), so the stale hover position was overriding the live selection anchor; a capture-phase pointerdown that is NOT on a `.wb-connect-dot` now clears `hoverAnchor` so the selection anchor (which tracks the move frame by frame) drives the dots, while a drag that starts ON a dot keeps the anchor because that IS the connector drag. Drive asserts the shadow is locked+linked and follows a moved face, that double-click still binds a label, and that the 4-dot centroid stays on a shape's centre mid-drag (centreGap 0). **Tools now ARM the Miro way (2026-08-26, "mirror how Miro works, that's your north star"):** clicking the sticky tool no longer drops a sticky at centre; it ARMS placement (`placingSticky` holds the armed colour, `body.wb-placing-sticky` shows a crosshair, the colour flyout stays open) and the next CANVAS click drops one WHERE you click, staying armed to place more until Escape or another tool (N arms it too; Excalidraw's own tools already arm via `setActiveTool`). The placement handler is a capture-phase pointerdown that converts client to scene coords, places via `placeStickyAtScene` (which passes `scroll:false` so the viewport does not re-centre and jump on each drop), and `stopPropagation`s so Excalidraw never also starts a selection; rail/style-bar/connect-dot targets are not placements. Drive spec asserts that clicking the tool drops NOTHING until a canvas click, that the sticky lands at the click point (at 100% and 40% zoom), that picking a colour then clicking places that colour, and that Escape clears the armed state. **The sub-panel and cursor are Miro's now (2026-08-26, Pat's Miro screenshot):** the armed flyout is Miro's full 16-colour sticky palette (`STICKY_COLORS`, sampled from Miro's DOM) in a 2-COLUMN grid (`.wb-flyout-swatches` `repeat(2, ...)`), and `body.wb-placing-sticky` sets a little sticky-note SVG cursor (not a bare crosshair) so you can see you are in placement mode. **The flyouts open to the RIGHT of the rail and were being CLIPPED INVISIBLE (drive-caught, the panel measured on-screen but painted nothing):** `.wb-rail` had `overflow-y:auto` for its height cap, and `overflow-y:auto` forces `overflow-x` to clip, so the right-opening flyouts were cut off; with 15 tools the rail fits every real window without scrolling, so the overflow is removed and the flyouts show. **The tools sweep (2026-08-26, Pat: "3 fucking shapes? no way to edit text in a shape, arrow just kept going") added the shape set, the arrow-finish cue, and the text-edit unblock, all driven and screenshotted before shipping (rule 16).** Three findings from driving the real board, each fixed at its root: (1) the arrow "never ends" is Excalidraw's multi-point mode (a click, not a drag, starts placing points; Escape/Enter/double-click all finish it, verified, but nothing said so), so `WhiteboardCanvas` reads `appState.multiElement` and shows a `.wb-hint` pill ("Placing a line. Double-click or press Enter to finish, Esc to cancel"), and the style bars hide while it is up so the hint stands alone. (2) "no way to edit text in a shape" is a FALSE report of the gesture but a TRUE interaction bug: double-click-to-add-bound-text works natively, but the hover connect dots sat ON the shape edges and ate clicks meant for the body, so `anchorForElement` now offsets all four dots `CONNECT_DOT_GAP=13`px OUTSIDE the edges (Miro-style; the connector still binds to the real edge, the dot is only the grab) and the dots are suppressed while a text editor is open (`editingElement`); the old drive assertion that dots sit ON the edge was updated to require the outside offset. (3) "3 shapes" is now 16: `board-files.cjs` `SHAPE_DEFS` holds the four native container shapes (rectangle, rounded, ellipse, diamond: Excalidraw's own tools, so drag-to-draw and double-click bound text) plus twelve POLY shapes (triangle, right-triangle, pentagon, hexagon, octagon, star, parallelogram, trapezoid, block-arrow, chevron, cross, speech) built as CLOSED FILLED `line` elements (verified to render filled in 0.18.1) via `shapeSkeleton`, each marked `customData.polyShape` so `selectionIsConnector` treats it as a SHAPE (fill/colour bar) not a connector (routing/arrowheads bar), which was the one real trap: a poly is a `line` under the hood and without the mark showed the wrong style bar. - **The Miro-parity waves A (connectors) and B (sticky/canvas), 2026-08-30, live-measured against real Miro.** Ground truth is `~\.cache\harbor\miro-parity-2026-08-30\miro-catalog.md` (81 numbered findings with exact hexes and thresholds, driven in Pat's real Miro) plus `miro-diff-plan.md` (verdicts and Waves A-D; C is the contextual floating toolbar above the selection, D the shape catalog and context menus). Wave A (merge `5b19f2b`): every connector decision is PURE in `board-files.cjs`; the canvas JSX only executes them. Drag-from-dot snapping is `nearestAnchorSide`/`connectorPlan` (`SNAP_RADIUS` 24 screen px; the drag's start side is always honoured, the target side comes from the drop point, else the side facing the source). While an end is dragged, `classifyDragPoint` implements Miro's two-tier targeting (`EDGE_REVEAL` 25): within snap radius of a side midpoint = 'dot' (the ring fills solid `#4262ff` and the head parks on it), inside the body = 'body' (the whole shape glows and the preview head parks where the segment first crosses the border, `segmentBoxEntry`), near the edge = 'edge' (rings reveal, nothing lit). Target rings render ON the border (`edgeMidpoints`) while the SOURCE dots float `CONNECT_DOT_GAP` 19px outside. **A body drop pins through Excalidraw's OWN binding model**: `bindingFocusFromDrop` ports `determineFocusDistance`/`determineFocusPoint` from 0.18.1 exactly (angle 0) and the binding is `{ focus, gap: 0 }`, because `updateBoundPoint`'s gap===0 branch lands the recomputed endpoint ON the focus point, so the endpoint travels with the shape and the entry edge migrates when the shape later moves; a DOT drop is `{ focus: 0, gap: 6 }` (side midpoint, small standoff). Dangling ends are legal (Miro allows them), endpoints re-drag and re-snap, a mid-line drag subdivides into a bend, elbow segments drag sideways, elbow routing clears shape bodies by `ELBOW_CLEARANCE` 28 with ~8px corners, and curved is the default routing.
