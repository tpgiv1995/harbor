# Harbor doctrine: sends, dialogs, transcripts, and the command bar

Part of CLAUDE.md. The single file crossed the Claude CLI's 150k-char auto-load limit on 2026-08-29, so the per-area doctrine moved here VERBATIM; nothing was rewritten. Everything below carries the same force as CLAUDE.md itself. Read this file BEFORE touching `main/session-send.js`, `main/menu-parse.js`, ask cards / pending-ask, adopt-on-send / takeover, `main/providers/transcript.js`, the context gauge or cache chip, `stage/Conversation`, `stage/CommandBar`, `stage/ComposeEditor`, drafts, attachments and file drop, spellcheck, or voice mode.

Slate data plane (added 2026-07-18): `main/providers/transcript.js` tails and parses each open session's JSONL into conversation blocks (mass-tested against the full 1,400-file corpus); `main/session-send.js` is the command-bar engine; pane resolution, provisional session↔pane links (snapshot-diff discovery beats the 60-150s agent-detection lag), resume-then-send queueing with readiness polling, and honest failure statuses (`send:status` push). The **context gauge NEVER invents a denominator** (Pat mandate 2026-07-21, after the fifth wrong-percentage incident in four days, each one a guessed window: family defaults, assumed 1M, a table missing `claude-fable-5`). A percentage comes only from Claude's own math: the statusline tee at `~/.cache/harbor/context/<session>.json` (`used_percentage`, authoritative while fresh or while the transcript has not outgrown it), a window the tee now hands over directly (`context_window_size`, teed since 2026-08-12, persisted to `<session>.learned.json`), or a window LEARNED numerically from a pairable tee (`pct = tokens/window`, persisted the same way, clamped to [50k, 5M], survives restarts, re-learns on >10% drift so a mid-session model switch corrects within one statusline repaint). With none of those, the chip and the `CTX` footer show the honest token count (`151k`), never a percent. There is NO per-model window table anywhere in the code; do not add one. The **cache chip** beside the gauge (2026-08-21) follows the same posture: warm/expired derives ONLY from the transcript's own assistant usage records (the `cache_creation` ephemeral_1h/5m breakdown names the TTL, the record timestamp is the last touch; facts captured in `transcript.js`, verdict derived at RENDER time in `renderer/stage/cache-freshness.cjs` on a 30s tick, because warmth expires with no transcript event to repaint on). A session that never reported cache fields gets no chip, and the warm wording promises relative speed only: a 470k-token cache HIT still measured 36s to first record, so warm never claims fast, only faster than cold.

**Outside sessions adopt on send** (`session:takeover` → `window.harbor.session.takeover`): when a session is live outside Harbor (transcript hot, no daemon pane), the command bar STAYS ENABLED and Enter moves the session into Harbor as part of the send: the adopt flow reads the statusline context tee at `~/.cache/harbor/context/<session>.json` for `{session_id, pid}`, verifies the process is Claude (the platform adapter's `processInfo` on win32; a `/proc/<pid>/cmdline` read on POSIX), terminates it (SIGKILL escalation if needed), resumes through `bin/claude-sessions --resume-id … --live-ok`, then delivers the composed text (and any image attachments). There is NO separate Take over button and no watch-only composer state (removed 2026-07-20: the two-click confirm dead-zoned natural click rhythms, and Pat vetoed the concept; the typed message IS the consent). An empty-composer Enter on an outside session is a no-op. **The readiness wait sizes the pane BEFORE it settles, and settles on MEANING not bytes (2026-07-28).** `waitForResumedClaudeReady` required two byte-identical reads 800ms apart, which was always luck (Claude's footer carries live cost/context numbers) and became impossible once panes get resized: a resize changes the wrap width and empties the daemon's `recent` buffer, so a sizing landing mid-wait makes every read differ from the last. An adopt that times out there is the most expensive way for a message not to land, because adoption has ALREADY killed and resumed the session ("session adopted, but Claude never became ready"). The pane is now sized once, awaited, before the loop, and `settleKey` compares the screen with its trailing status lines dropped and whitespace collapsed. The adopt path also writes to the send log (`sessionSend.logStatus`), because when it failed the only record anywhere was a truncated line in Pat's status bar. Missing or mismatched tee data still refuses honestly without resuming, and the refusal SAYS WHAT TO DO (the OWNER_UNKNOWN message was expanded 2026-08-13, because "cannot identify the owning process" alone told Pat nothing). But a VERIFIABLY GONE owner is not a dead end (live-caught 2026-07-24: an OOM kill left a working-tailed transcript and a dead tee pid, and the first Enter refused): a dead pid, a recycled pid whose process is no longer claude, or a zombie falls through to resume-then-send after a best-effort scan confirms no other live claude carries the session id; a scan hit refuses honestly and retryably, and the scan NEVER picks a kill target, signals stay strictly tee-verified. `createSessionOwnerProbe` carries a 3s deadline on both of its process questions (2026-08-03: a kernel wedge left process reads blocking forever; a probe that hangs is a probe that lies by omission). The renderer side of the same incident family lives in the `session-liveness` shared twins: `processAlive: false` (exact, pid-reuse-guarded, computed at emit time) outranks a stale `working` flag, because a session killed mid-turn freezes its transcript in a working state; status pushes on `send:status`. Adopting a session mid-turn kills its in-flight turn; adopting an autonomous loop session ends that loop's process and continues the conversation in Harbor.

- **A pane is not a session: the dead-shell guard.** The Claude CLI (a Bun binary) can SEGFAULT mid-session (live-caught 2026-07-22, crashing while dequeuing a queued image message), leaving its pty pane alive at a shell prompt; Harbor then typed the next send into that shell and the shell EXECUTED it. Three layers now make that state impossible: `resolvePane` rejects a pane whose snapshot `agent_session` names a different session (pane-keyed provisional ids skip the ownership test, the pane IS their identity); `assertNotDeadShell` (run for EVERY provider, inside `assertComposerSafe` for claude) refuses a bare shell-prompt tail (`SHELL_PROMPT_TAIL_RE`, error code `DEAD_SHELL`, with an `esc to interrupt` working-turn short-circuit so a mid-turn claude is never mistaken for a shell) and `runSend` catches that code and falls through to resume-then-send so the message still delivers (a pane-keyed send keeps the honest refusal instead); and the sidebar bridge drops a pane's agent facts on `agent_status: 'unknown'` (no foreground agent) or a pane update carrying explicit null agent fields, so a crashed session goes gray in the rail instead of staying green for 90 minutes (index.js also drops the provisional pane link on 'unknown'). Stand-in test panes must satisfy the contract (a raw shell pane can no longer receive a send, by design). Never re-broaden the pass-through to cover shell prompts, and never treat pane existence as session liveness.
- **A claude transcript is found from DISK, not only from the index (2026-07-28).** `findProviderTranscript` handled cursor and codex and let claude fall through to `return null`, so the only way a claude window ever found its transcript was `meta.path` from the harbor index. A session younger than the index therefore opened to "No transcript yet" and STAYED there, because the renderer marked a failed open as missing and never asked again. Pat hit it twice that day, the second time on a session already 190 lines deep and plainly on disk. The path is derivable (`<cwd munged>/<session id>.jsonl`) and the id is unique, so a miss now falls back to scanning the project dirs for the file, and a failed open is RETRIED (the id leaves the open set, and a 3s tick re-runs the pass) because "not yet" is not "never": a brand-new session writes its transcript on its first message. **The QUESTION CARD was left behind on the old behaviour and had to be fixed the same way a day later (2026-07-29), which is why this rule is about the INDEX and not about one view.** `liveAskFor` resolved its transcript only through `sidebarBridge.getSessionMeta().path` and then cached the answer INCLUDING A MISS, permanently, so a session younger than the index poisoned its own card on the first 700ms poll and no later poll ever looked again for the life of the app process. That failure is silent and mis-shaped: the card still renders, still lists the option rows the pty can see, and loses ONLY the question heading and the option descriptions, because those two come from the transcript and nothing else does. Pat reported it, bluntly, as being unable to see the question he was supposed to answer, his second report of that card. The decision now lives in `main/ask-transcript-path.js` (`createAskTranscriptResolver`) with the two rules stated as specs: the index is a CACHE and `findProviderTranscript` is the fallback, and a MISS IS NEVER CACHED while a hit is. Diagnosed against the real 4.9MB transcript of the session that failed: the reader, the merge and the renderer were all correct, and every one of them was starved by the path lookup. When adding a consumer that needs a transcript, resolve it through the same helper; never re-derive "ask the index and give up". **THE SESSION'S OPENING PROMPT IS NEVER OUT OF REACH (2026-08-13, Pat: "my first messages in each session are getting lost").** A tile initializes a large transcript from its last `MAX_INITIAL_BYTES` (1MB), so the first thing he typed, the message the whole session is an answer to, fell outside the parsed window and the window opened on Claude replying to nothing. It is not a rare edge, because **a pasted screenshot rides in the JSONL as base64**: measured on the real transcript he reported, the opening user line was **1,109,121 bytes against a 1,048,576-byte window**, so one image-bearing first message is routinely larger than the entire window. That message was unreachable from BOTH directions, which is why nothing already in the file rescued it: too big to fit in the tail, and `readPrefixImageBlocks` reads bytes `0..tailStart-1`, which **cut that same line in half**, so its `JSON.parse` threw and the image seeder dropped it too (the images survived from later records while their own text did not, which is exactly the "answering a question that isn't there" shape). `readOpeningBlock` therefore reads FORWARD from byte 0 in chunks and stops at the first user block, so the common case touches a few KB and a multi-megabyte first line is still read whole; `seedOpeningBlock` pushes it before the prefix images and before the tail, so it lands at the top of the tile where it belongs, and it hands the block to `seedPrefixImages` so a SMALL first message (which the image scan can reach) is not pushed twice. `MAX_BLOCKS` trimming already protects user turns and image-bearing blocks, so the opening survives a long session. Windowed (mobile) opens skip it for the same stated reason the image seeder does: the payload is trimmed to the most recent blocks and pages back instead. Proven two-sided against a fixture whose first line exceeds the window (fails at HEAD, passes here) and live against the 3.9MB transcript he reported, which now renders his opening ask as row one with both screenshots attached.

**Conversations render from transcripts, the pty is for driving.** Session windows parse `~/.claude/projects/**.jsonl` (works even for sessions running OUTSIDE Harbor; sending into one adopts it first, see "Outside sessions adopt on send"). The command bar writes to the pty of the SELECTED window only, via exclusive control through the sessiond supervisor; a dead session is resumed first through `bin/claude-sessions` and the composed text delivered when Claude's composer settles; never silently dropped.
- **Questions and dialogs are answered IN the window, and there are FIVE dialog shapes.** `main/menu-parse.js` recognizes the AskUserQuestion select menu ("Enter to select ... navigate"), the permission/hook confirmation ("Esc to cancel · Tab to amend · ctrl+e to explain"; live-caught 2026-07-20 as a send dead end when only the first was known), the FOOTERLESS resume-from-summary dialog (`RESUME_SENTINEL`: "Resuming the full session will consume ..."; options 1 Resume-from-summary / 2 Resume-full-session-as-is / 3 Don't-ask-again), and the viewport-CLIPPED menu (live-caught 2026-07-21: long option descriptions overflow the pty viewport, cutting the question, option 1, and the `❯` pointer off the top; the clipped top is unrecoverable, the pane buffer holds only the visible screen). A resume auto-answers option 2 via `answerMenu({ type: 'select', index: 2 })` inside `waitForResumedClaudeReady`, landing the session at a real composer without a `>_` detour; the self-correcting arrow walk keys on the option NUMBER under the `❯` re-read each step (positions in the visible run shift when the list clips or scrolls, and a position-keyed walk selects the WRONG option), only presses Enter once the `❯` is verified on the target number, and a `select` action delivers NO text. `SessionTile`'s `TileMenuAsk` card polls `session:menu-state` (700ms) and answers via `session:menu-answer`; a clipped menu renders the visible tail with real numbers and never a fabricated question. **There is no "the question text and option 1 scrolled out of the terminal view" note any more, and none may be added** (Pat, 2026-07-27): it was never information he could act on, only a confession that Harbor was driving a 23-row pane at a 35-row dialog, and both halves of that are fixed below. `parseMenu` only trusts a footer at the BOTTOM of the scrape (a stale answered-menu frame above a fresh composer must not render a ghost card) and keeps only the trailing consecutive option run; a run starting above 1 counts as a clipped menu ONLY when its last option sits directly above the footer (blank/divider lines only in between), else it is numbered prose. A send into a parsed question refuses with "asking a question in its window". **The no-dead-end guard (Pat mandate 2026-07-21): a blocked pane must ALWAYS be answerable in its window.** When the screen is a blocker the parser does NOT recognize, `session:menu-state` returns `{ fallback, screen }`: the classifier reads the RECENT scrape (a pane resize on link can scroll a live one-shot dialog's top into scrollback, so the visible grid lies), decides live-vs-dead by the TAIL (a resolution tail: lone-`❯` composer, esc-to-interrupt, or bare shell prompt means the blocker above is a ghost, no panel), then panels on `BLOCKED_RE` or the shape-independent daemon `blocked` hint. **A COMPOSER IS A COMPOSER EVEN WITH A DRAFT IN IT, and a POINTER IS NOT A COMPOSER (both live-caught 2026-07-28).** The resolution test demanded a LONE `❯`, so a session sitting idle with text typed into its prompt (`❯ push the guard`) failed it, and Claude's own prose ("Ready to dig in, or do you want me to dive deeper on anything?") matched `Do you want` mid-sentence: Pat got a "needs your answer" panel covering an idle session, which is worse than the dead end the panel replaced. Widening the test to "any `❯` line" breaks it the other way, proven by a real capture of the same pane an hour later: the `/rewind` dialog's selected row is `❯ (current)`, no number and no chrome, and it genuinely needs an answer. The discriminator is the BOX EDGE, not the pointer: Claude draws its composer with a full-width divider immediately above the `❯`, so `isComposerLine` requires a lone `❯` or a divider directly above, and never a numbered row. `isBlockedScreen` is likewise split into dialog CHROME (which only a dialog draws) and a confirmation question anchored to the START of a line. A pane whose agent_status is `blocked` shows the amber "needs your answer" cue, and agent-status NEVER overrides the transcript's fresh working signal (agent detection lags 60-150s; either source saying working wins). **A dialog is a LAYOUT, not a list of lines (2026-07-26, from Pat's screenshot of a card that was functional but read as unfinished).** A batched AskUserQuestion draws a tab strip over several questions (`←  ☐ Control  ☐ Chart win…  ✔ Submit  →`), wraps its option labels, carries a description per option, and when the pane is wide parks that description in a BOXED SECOND COLUMN beside the options; read line by line that glued frame glyphs onto every label (`Custom segment +   ┌──────────┐`) and built the question out of three lines of transcript prose plus the strip. `parseMenu` therefore: finds the column gutter (the first column every row clears by two spaces and whose right side is framed, so a single-column menu can never match) and reads labels from the LEFT column only; takes the question from inside the dialog's own top divider, never from the transcript above it; rejoins every terminal wrap the way the pane broke it (no space when the previous line filled the pane and the fragment starts at column 0, a space otherwise), which is one rule fixing four separate corruptions (a hard-wrapped label, a wrapped tab strip fragment landing in the question, a wrapped footer hiding its own keys, and a question rejoined as "a custo m range"); keeps per-option `description`; and lifts `(Recommended)` out of the label into a flag. Frame glyphs NEVER survive into a label or description (`cleanText`). The two sources now split by AUTHORITY and neither substitutes for the other: the **transcript says what was asked**, the **pty stays the authority on the live interaction** (is the dialog still up, which row the `❯` is on, the option NUMBERING the walk keys off, which keys the footer offers). Building a card from the transcript alone would render a question answered ten minutes ago and type arrows into a composer. `main/ask-question.js` owns the merge (`normalizeAsk`, `mergeAsk`, `matchQuestionIndex`), `main/providers/pending-ask.js` reads the live question, and `session:menu-state` passes it in. The merge is **additive by contract**: an unmatched question set leaves exactly the old behaviour, which is what makes it safe in a 700ms poll. A merge NEVER touches a permission/hook confirmation (its footer says `Tab to amend · ctrl+e to explain`, and a session can easily hold an unanswered question while one of those is on screen), every visible row inside the payload's own 1..N numbering must be one of that question's options (a row the payload has never heard of disqualifies the match), and a TRUNCATED label only counts when at least 8 characters survive. All three were gate-caught on 2026-07-27, when the on-demand read made a real session's pending question reachable and `Yes` prefixed `Yes, ...`: the card retitled `Do you want to proceed?` with a question about a kernel fault. Because the visible options belong to exactly one question, WHICH question of a batch is current is now DERIVED rather than guessed, and the strip shows real `header` values instead of truncated tab labels. Options the pane cannot draw are listed from the transcript, marked `offscreen`, and ARE clickable: the walk keys on the option NUMBER and re-reads after every keystroke, so it steps the highlight up until the row scrolls into view and only then presses Enter, and it refuses out loud (`.tile-ask-err`) if it never can. Notes became a real per-answer control using whichever key the footer advertises (`notesKey`), replacing a sentence telling him to go to the terminal. The card scrolls internally with a VISIBLE scrollbar and takes at most 68% of the window: a fixed 244px list with an invisible scrollbar is what "i am scrolled down as far as possible and its still cut off" actually was.   **The root cause under all of it: the pane was 23 rows and the dialog needs 35 (2026-07-27, Pat's second report the same day, asking never to see the note "the question text and option 1 scrolled out of the terminal view" again, having asked more than ten times).** Four "the question scrolled out of the view" incidents (2026-07-21 through 2026-07-27) were one thing, never measured until now: a fresh pane was **23 rows x 54 columns**, Claude Code's AskUserQuestion dialog needs about 35 rows at that width, and the pane keeps NO scrollback, so the question, the one-tab strip and option 1 are gone before any parser sees them. Everything built on top (the clipped parse, the offscreen rows, the honesty note) was decorating a pane that was simply too small. Proven on a real dialog in an isolated pane, both captures kept as fixtures: at 23x54 (`test/fixtures/clipped-menu/real-claude-23x54.txt`) the read is the shape of Pat's screenshot; resize the pty to 120x60 and Claude redraws the whole dialog live (`test/fixtures/askuserquestion/real-claude-120x60.txt`), question, descriptions and the `❯` on option 1 included, because **Ink re-renders on SIGWINCH** (the 2026-07-21 note that a one-shot dialog does not is wrong for this family). So the stream supervisor's `ensureDialogSize` grows the pty to **120x60** and `terminal-bridge.ensureDialogSize` calls it from `getMenu`, once per pane the first time a window polls it (a second after the window opens, long before Claude asks anything) and again, rate-limited, whenever a read still comes back `clipped`, which heals a dialog that is ALREADY up. Only a CONTROLLER can resize (an observer attach provably cannot), so when Harbor is not already controlling the pane it attaches a short-lived control child, waits for the frame that proves the grant, and releases; the size outlives the release, `this.controller` is never touched (one controller per PANE, so sizing A cannot disturb control of B), and a pane someone else controls simply refuses, which is a skip. **A pane with the `>_` view open is never resized behind it**: that xterm's fit is the size the human chose. `readMenu` reads 90 lines to cover the taller pane, since reading fewer lines than the pane is tall would recreate the clipping one layer out, and **every pane read tries `recent` then `visible`**: a pty resize EMPTIES the recent buffer, and a full-screen TUI then redraws over the screen without pushing a single line into scrollback, so `recent` can come back 0 bytes while the dialog is plainly on screen (measured against a real pane right after Harbor grew it; gate-caught as six pty specs failing on empty reads). Reading only `recent` would make the card vanish at exactly the moment the pane was fixed. Guards: `test/main/dialog-size.test.js` (all behavior drives the sessiond supervisor, including a direct resize-request proof; the old herdr real-pty suite is retired with its backend).
