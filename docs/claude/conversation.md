# Harbor doctrine: sends, dialogs, transcripts, and the command bar

- **ONLY PAT MOVES A CONVERSATION WINDOW; EVERYTHING ELSE PUTS IT BACK (2026-11-16, Pat: "when im minimized out of a chat/session for some reason the windows sometimes just scroll to the top of the chat", plus a screenshot of four windows sitting on their first prompt).** A window is FOLLOWING (pinned to the latest message) or READING (a message held at a fixed offset from the window's top while replies arrive below). `renderer/stage/conversation-scroll.cjs` owns the rules (`createPlaceKeeper`, `restoreTarget`), `use-conversation-scroll.js` applies them to the page, and every top-level row in `Conversation.jsx` carries `data-anchor` so a reading window can be put back on its message. Only Pat's input changes the place: wheel, a pointer held on the window (scrollbar drag, text selection), the scroll keys and Tab with focus outside an editable, a send from the command bar (`harbor-conv-follow`: it follows again), and the wheel or PageUp/PageDown routed from the stage (`harbor-conv-scroll`). Any other scroll movement is the browser's, and the window is put back: on that scroll event, on every ResizeObserver change of the window or its content, on each block update, and on window focus and resize. Scrolling up leaves FOLLOWING at the first notch (`starting`), before the smooth scroll moves the box, so a reply landing mid-gesture cannot pull Pat down; scrolling down within 56 px of the bottom follows again. A message trimmed out of a loaded window turns it to FOLLOWING; one still loading is waited for. Places are remembered per session id (64, in memory), so the Tasks view and back or the `>_` toggle reopen where Pat was. **What the old code did wrong, measured on the real renderer** by `scripts/drive-conversation-scroll-win.js` (isolated, off-screen, three 30-turn chats): it read EVERY scroll event as Pat's, so any reflow (a third window opening: two windows left 426 px short; a 1x1 collapsed page standing in for a minimize: a window stopped following and missed the reply that landed meanwhile) turned following off for good; and a rearrange moved tiles in the page (next bullet in `views.md`), which resets a scroll box to its top with no event, so idle windows sat on their first prompt until the session next wrote. That drive fails 10 of its 14 checks on the old build and passes all of them on this one; `test/renderer/conversation-scroll.test.js` pins the rules. Never set a conversation's `scrollTop` from other code expecting it to stick: route it through `harbor-conv-scroll`, or it is put back. **The phone runs the same rule** (`app/web/src/conversation/Conversation.jsx` imports the hook; its "Latest" pill calls the hook's `follow`), keyed one view per session in `AppShell.jsx`, because one reused view carried the last session's scroll into the next. Two refinements came with it and apply to both: a scroll Pat started keeps counting as his while it keeps moving (each of his scroll events extends the grace), so a touch fling's glide is never yanked back after the browser cancels the pointer; and the window's own corrections are announced (`expect`) and answered `'ours'`, so they never extend that grace, or replies landing every half second would keep "Pat is scrolling" alive and let a browser nudge through as his. A drive that tests scrolling must use real input (CDP wheel or `Input.dispatchTouchEvent` drags; `Input.synthesizeScrollGesture` does not scroll the chat in the headless phone harness): `scripts/drive-phone-ux-win.js` states `jump`, `scrollHolds`, `follows`, `sessionSwitch`, `times`.
- **EVERY PROMPT AND REPLY SHOWS ITS TIME, IN THE MACHINE'S ZONE (2026-11-16, Pat: "time stamps on messages in harbor (from the agents + from me) ... needs to be in my timezone").** Blocks already carried the transcript record's `ts`; `renderer/stage/message-time.cjs` prints it with the system zone and locale (never a pinned zone: the public build runs elsewhere, and a laptop that travels shows local time): "3:38 PM" today, "Yesterday 3:38 PM", "Mon 3:38 PM" within the week, then "Nov 9, 3:38 PM" and the year when it differs; the hover title is the full date with the zone. Under a prompt the time leads the turn line ("3:38 PM · ↓ 4.2k tokens · 38s"); under a reply it is its own quiet line. One timer for all windows re-renders the labels at local midnight. The phone shows the same labels in the phone's own zone (a quiet line under each prompt and reply); `subscribeDay`/`currentDay` in `message-time.cjs` are the one midnight timer both use. Progress notes and tool rows carry no time on purpose.

- **A NON-CLAUDE PANE THAT HAS DRAWN NOTHING IS NEVER TYPED INTO (2026-11-09, CLI review).** A fresh Cursor pane draws nothing while its MCP servers start: 35 to 45 s in saved runs of 2026.11.05, over 60 s on the old build under load. Before this, the first send waited 15 s for a drawn pane and 45 s for a blank one, then logged "sending anyway" and typed into a pane that was not listening. `waitForProviderReady` (`main/session-send.js`) now gives a pane that has drawn NOTHING a 90 s boot budget by default (the Resume buttons in `main/index.js` and `server/compose.js` call it with no options, and kept 45 s until the second review caught it). A drawn pane that never settles keeps its old 15 s or 45 s and is still typed into, and a read that throws is no evidence of a blank pane. If the pane is still blank when the budget ends, the send is refused with `PROVIDER_NEVER_DREW` ("... has not drawn anything after 90 seconds, so Harbor typed and sent nothing. Your text is kept"), logged as the `provider-never-drew` phase with a send capture. After 15 s of blank, the status line says why the send is slow, once. Specs: `test/main/session-send.test.js` ("never draws anything", "says why the send is slow", "stays blank for 70 s", "with no options waits out").

Reopen this window to see it." when the store answers 404. `MAX_IMAGE_BLOCKS` is now `MAX_BLOCKS` (no separate image cap; `trimImages` stays as the guard for the day a block carries bytes again); a window seeds at most `MAX_PREFIX_IMAGE_BLOCKS` (64) images from the part it does not read, older prompts keeping their words. - **RETURNING TO THE PHONE APP IS NOT A RELOAD (2026-10-11, Pat: "if i leave the app for like 5 seconds and return to it (without closing the app) it reloads and takes a while. also ... doesnt show like session context").** Measured on the live server: every phone (re)connect fetched the whole rail model (3.96 MB, 4,368 rows), received the same 3.96 MB as a push, and re-fetched it every 15 s, while the drawer shows 48 hours; and `rpc/client.js` waited a fixed 4 s after iOS closed the backgrounded socket. The rules now: (1) the phone gets a PROJECTION (`src/server/phone-rail.js`): live, waiting and blocked rows plus the requested window (48 h default for get-state and every push), with search across all history answered on demand by `sidebar:get-state { query }`, capped at 300 with live rows never cut; the drawer's 7d/30d/All and search fetch their slice and overlay the push (`rows.js mergeRailModels`, pushed rows win); no 15 s full poll (a 60 s safety refresh of the small projection). Live rows carry `contextPct` from the statusline tee, never a guess. (2) The client reconnects at once on visibilitychange, pageshow, focus and online, proves a socket that still says open with one `daemon:get-banner` round trip (replaced after 2.5 s of silence), and backs off 250 ms, 1 s, 2 s, 4 s only for repeated failures. (3) A drop shows a small "Reconnecting" pill for its first 5 s, never the error panel, and the drawer stays usable from the held list. (4) The last list and the last four conversations' recent blocks live in localStorage (`rpc/local-cache.js`) and paint on a cold boot; a cached header reads "Last seen working", and incremental pushes are ignored until the server's replace arrives. Anything that reads over RPC on mount must skip while disconnected and re-read on reconnect (use-send's queue read and use-capabilities did neither, which showed "not connected" in red and an empty slash menu after a cached boot); the session screen mounts only once the RPC client exists. (5) The header shows the context ring (tokens when the window is unknown), "Working 1m 12s, tokens", "Waiting on you" or "Idle 12m", and prompt-cache warmth, using `turn-meta.cjs` and `cache-freshness.cjs` like the desktop; `session:work-meter` is remote-safe since this date (numbers only, read-only). (6) harbor-server exits for a respawn when its daemon links keep failing while a FRESH control client still pings the daemon (`src/server/link-watchdog.js`), and stays up when the daemon itself is down. It counts separate BURSTS of link errors (a gap over 5 s starts a new one; 4 bursts in 120 s trip it), never single errors, since 2026-10-20: one daemon stall over the 10 s request timeout destroys the client socket and fails every in-flight request in the same millisecond, so the old 4-error rule restarted the server on every stall (64 restarts, about one every 3 minutes that afternoon, each re-reading about 3 GB at startup), while a truly stale link fails every poll and still trips in under a minute. Proof: `test/server/phone-rail.test.js`, `test/server/link-watchdog.test.js`, `test/web/phone-return.test.js`, and `scripts/drive-phone-return-win.js` (isolated composition, synthetic sessions, headless Chromium at iPhone 14 size; 28 KB on connect against 3,000-row history, cold boot from cache with the pill). A synthetic fixture whose cwd sits under Temp is hidden by the throwaway-directory rule in `filterProjects`; give fixtures a normal folder.

- **EVERY PHONE WAIT HAS A DEADLINE, AND "COULD NOT ASK" IS NEVER "NO" (2026-10-21, Pat's phone on "Connecting…" at 08:14 while the server answered loopback in 4 ms).** An adversarial review on GPT-6.1 Sol (`C:\dev\.harbor-scratch\phone-2026-10-21\sol-reliability\findings.md`, each finding reproduced) found the client waited on things that never end. `web/src/rpc/client.js`: a handshake still CONNECTING after 6 s is abandoned and retried (it waited for the OS TCP timeout, and `wake()` ignored a CONNECTING socket); coming back to the app replaces a handshake older than 1.5 s; while visible, an open socket is proven every 20 s and one silent for 5 s is replaced, failing what waited on it (a swallowed socket kept saying OPEN and a send spun forever); `reconnectNow()` backs the Retry buttons. `probeAuth` has a 4 s deadline and reports `unavailable` for a network failure or a 5xx, which `setup-gate.cjs` HOLDS and retries instead of reading it as "token required" (that sent an offline phone to the paste-a-token screen), and a phone with a stored token never waits on /whoami at all. `web/public/sw.js` opens the saved app when a launch gets a 5xx (`tailscale serve` answers a restarting server with a 502, a resolved fetch the catch-only fallback never saw), an error, or nothing within 3.5 s; 4xx refusals still reach the page. ONLY A DOCUMENT THAT WAS SERVED IS SAVED, and its copy is cloned synchronously: the first version let a late answer replace the saved shell after the old one had been served, a page whose hashed bundle was never fetched, so the next offline launch was blank (second Sol review, P0, reproduced in Chromium), and a clone taken after the page started reading the body saved nothing at all. A refused cache write never costs the response. Every RPC has a deadline (45 s reads, 240 s actions that may wait on a starting session); a timed-out action says it may still have happened and is never resent, and an acknowledged send no longer waits on its queue refresh. The auth probe counts only its NEWEST answer, an "unavailable" never replaces an earlier success (a late 503 had unmounted a connected app), and a phone the tailnet authenticated before opens its saved app while the server cannot be asked. A session picked from 7d/30d/All/search is kept by the shell (and across a reload), since the held rail is the 48 h projection and the pick used to land on "Choose a session". The question card's poll skips while hidden or disconnected and no longer clears a waiting question on an undeliverable call. Proof: `test/web/phone-return.test.js` (handshake timeout, stale handshake on wake, heartbeat, retry), `test/web/setup-gate.test.js`, `test/web/service-worker.test.js` (fails on the old worker for the 502 and slow cases).
- **THE PHONE SERVER NEVER WAITS, FREEZES OR DIES ON ONE BAD INPUT, AND SENDS WHAT CHANGED (2026-10-21, same review; server batch).** (1) `providers/artifacts.js` found paths with a regex that retried suffixes from every slash, so one slash-rich base64 image record held the event loop 18.5 s (desktop and phone alike); each slash chain is now scanned once, runs of 1 KiB+ base64 are blanked first, output proven identical on 6,000 cases. (2) `server/link-watchdog.js` has a loop-lag monitor (logs `event loop lag observed`), and a link error with a server stall of 2 s or more inside its request's lifetime (10 s timeout plus 5 s) does not count toward a trip: a request 8 s into its budget misses on a 2 s stall, so the first rule (only stalls of 10 s+) still restarted on four 8 s stalls (second review). (3) A token tick re-marked the turn's prompt and resent it whole, image included (1.57 MB per 15 s to the phone): a block whose images the client already holds now goes in `patched` without them, and the ONE reducer (`shared/transcript-blocks.cjs`) merges a patch over the held block, keeping its images; a usage record that moves nothing sends nothing. (4) `transport/ws.js`: a socket error ends that socket only (a two-byte bad frame used to kill the server), the byte cap is checked AFTER a coalescing merge (one key, one copy, newest wins), and `transcript:update` goes only to clients holding that session or with an open in flight (`client-resources.holds`), an open's snapshot only to its requester. (5) `server/index.js` stamps every log line with an ISO time and a failed boot exits after 2 s instead of idling non-listening forever. Still open: the server listens only after its whole boot (about 60 s on the Legion, measured 2026-10-21 09:20:44 to 09:21:48), and a session's first snapshot carries its images inline (8.6 MB for one screenshot-heavy chat).
- **TRIMMING A TRANSCRIPT IS A DELTA (2026-10-11).** When the bounded transcript drops its oldest blocks, transcript:update carries removed keys alongside append/changed.
