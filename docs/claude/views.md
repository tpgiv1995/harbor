# Harbor doctrine: the rail, stage windows, and the Tasks / Notes / Files / Orch views

Part of CLAUDE.md. The single file crossed the Claude CLI's 150k-char auto-load limit on 2026-08-29, so the per-area doctrine moved here VERBATIM; nothing was rewritten. Everything below carries the same force as CLAUDE.md itself. Read this file BEFORE touching `renderer/sidebar/`, stage window chrome, unseen-completions or the taskbar badge, project icons, usage meters, the WorkflowStrip, `ViewSwitch`, the Tasks view or `bin/harbor-tasks`, the Notes view or `bin/harbor-notes`, the Files (artifacts) view, or orchestration surfaces.

**DELEGATED CHILDREN ARE NOT CLAUDE-DELEGATE BATCH WORKERS (2026-09-26).** `delegatedBy` is a separate identity from `isChildTask`. The latter drives queue batch-liveness candidates, terminal worker grouping and the workers chip, and those consumers remain batch-only. Codex subagents/guardians belong to their metadata parent; a linked exec root belongs to the dispatching Claude session. Delegated history is hidden from the rail until search includes it, but a live pane stays visible. Unlinked exec roots stay ordinary rows. The sidebar-model JS/CJS twins make the same decision. Delegated children are excluded from open-live, unseen completions, the taskbar attention map, the ask-hook inbox and titling. Title formatting still uses batch childTitle only for actual batch workers; delegation titles come from metadata. Do not set isChildTask to achieve any of this. The bridge keeps history rows in an id Map for delegated lookup and notification checks; rebuild it whenever the history array changes, not once at startup.

**THE ORCH OVERVIEW INCLUDES DELEGATED AGENTS (same incident).** Its new section groups by parent, lists task descriptions and prompt headings, provider/model, rounds, outcomes, last-signal age, named children and a plain approval-review count. Parent and child clicks open their conversations. Other background commands and monitors are compact inventory. A reviewer count is plain text, not an expander with no useful contents. Background chips carry a static blue dot; ages under a minute say <1m. Active groups come first; done groups use the existing ten-minute linger. The thirty-second overview poll ages evidence from memory so quiet work actually becomes quiet without another write. Sidebar pushes refresh only the delegation data, through single-flight; they must not call the queue-run history builder. Review reproduced 41 concurrent queue scans from 40 pushes before that separation. The rate regression test drives the actual component. `orchestration:list-delegations` is registered in preload, method registry, remote-safe registry, both compositions and the RPC tests. Native taskbar badges still consume the same attention map as the rail; background work cannot create an unseen completion there.

**CLOSED PARENTS DO NOT PIN THE ORCH OVERVIEW (live validation, 2026-09-26).** Parent-owned tasks without a completion record read `ended with session` once the header's ownership rule says the owner is gone. They cannot keep a group active or visible forever. The recent-done clock uses the last real signal, never the time Harbor noticed the exit. A linked child with fresh rollout writes remains running independently. Closed-parent rounds without a terminal record say end time unknown. Test cached reads after a pane closes as well as a cold worker scan; the phone uses the same bridge read. Synthetic drive groups cover old hidden tasks, recently ended tasks and an independently running child.

**SILENT ORPHAN AGENTS ARE NOT QUIET FOREVER (same day's next live check).** A linked rollout older than the discovery window must still be read for its terminal event. Under a dead parent, no child evidence or ten minutes without a family signal means ended, with end time unknown for an unresolved round. It does not mean a successful result. Only fresh independent work can keep that dead parent's group active; visibility still ages from real signals. A live parent's silent agent keeps quiet, possibly hung. Apply the rule to child subtrees and cached reads too. The hidden drive pairs an old completed family that is absent from the overview with a recent closed parent whose silent child visibly reads ended, while the live quiet agent and independent running agent stay unchanged.

- **WHICH SESSIONS FINISHED WHILE YOU WERE AWAY (2026-08-14).** Pat runs 12-14 open windows with 4-5 actually working, closes Harbor for a while, and on return cannot tell which sessions completed a turn and are waiting for him. `renderer/stage/unseen-completions.cjs` is the whole rule and is PURE: a session is waiting when it is not working and its transcript clock has advanced past the last time he looked at it. That formulation is chosen because **Harbor observes nothing at all while it is closed**: `notify.js` watches live work→idle transitions for toasts, in memory, and dies with the app, so nothing built on watching transitions could answer the question actually asked. Two durable timestamps can. The store (`localStorage['harbor-seen']`) is a WATERMARK plus per-session checks: the watermark is stamped ONCE on first run, which is what stops all 719 existing rail sessions lighting up the day this ships, and is also the fallback for a session with no entry, so a session STARTED later still announces itself. It holds a timestamp per session rather than a flag, because a session finishes, gets checked, runs again and must be able to mark itself a second time; re-seeding is refused for the same reason (it would silently mark everything read). Selecting a window marks it seen and keeps marking it on every update while it stays selected, so a turn completing in the window he is watching never badges. Two cues, never one: `blocked` (waiting on an answer, amber, reusing the existing needs-your-answer vocabulary) OUTRANKS `finished` (accent), because they ask different things of him and a blocked session reported as merely done is a lie he would act on. Working/blocked are read from the OPEN transcript header where there is one and from the daemon's agent status otherwise, the same preference the voice settle-watcher makes, because agent detection lags 60-150s and this is a promptness feature. `activeMs` must be the TRANSCRIPT clock and never the rail's live heartbeat: `sidebar-model` stamps `lastActiveMs = now` on every refresh for a pane with no history row, and a clock that always reads "now" would re-mark a session the instant it was checked, forever (the `isHistorical` guard is what keeps those rows out). **The marker is on the project GROUP header as well as the row**, found by driving it rather than by reasoning: the attention map was computed correctly for 723 sessions and the rail still showed nothing, because a collapsed project renders none of its session rows at all, so a group with three finished sessions read as quiet. The window-header pip sits in the IDENTITY run (never `.wh-meta`, which the density rules wrap to a second line at 3-4 columns, precisely the crowded grid this exists for) and beside the TITLE rather than the project icon, whose fallback is itself a coloured dot that made two adjacent dots read as one control. Driven end to end offscreen: a fresh seed marks 0, a backdated watermark marks 17 projects, expanding one shows its rows marked, opening a session clears its row and persists the check while the other three stay marked, and a restored two-window stage shows the pip on the unselected waiting window and none on the selected one. **The same attention map drives a Windows taskbar overlay badge (2026-08-22)**: one overlay per taskbar button is all Windows offers, so AMBER with the blocked count wins whenever any session needs an answer (blocked outranks finished, the same precedence as the pips), else ACCENT with the finished count, else cleared; counts display 1-9 then 9+, the overlay description always carries both counts in words, `stage/taskbar-badge.cjs` is the pure plan, the renderer rasterizes the bitmap on a canvas (main cannot) and sends it over `window.harbor.badge.set` through ONE `createTaskbarBadgeScheduler` (in `taskbar-badge.cjs`), and the win32-gated main handler calls `setOverlayIcon` passively: it never focuses, flashes, or restacks anything. The scheduler coalesces a CHANGE of plan for ~250ms and sends only real changes, and an update that changes nothing must NEVER restart its clock: the App recomputes the plan on every transcript update of every open window, and the old effect that re-armed its own timer on each recompute meant no badge was sent while any window streamed (2026-10-04; `scripts/drive-taskbar-badge-win.js` records every IPC and overlay call from main's Node inspector: 0 sends in 36 updates before, sent within ~250ms after). **And nothing else may write the overlay slot: on win32 `app.setBadgeCount` is NOT a no-op, it writes the same overlay**, and notify's unacknowledged count (0 whenever Harbor has focus) wiped the badge every few seconds. Filmed live 2026-10-04 by attaching to the running main process: the overlay applied, `app.setBadgeCount(0)` erased it, an identical re-set while showing did not flicker at all. So the 2026-09-29 "blink" was that wipe-and-resend cycle, not Windows replaying identical sets (the diagnosis at the time), and deduping the resends turned it into "i dont get the blue / yellow alert numbers anymore". `setAppBadgeCount` returns early on win32, and main applies every set the renderer sends with no repeat guard, so a reloaded renderer heals an overlay something else cleared.
