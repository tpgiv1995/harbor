# Harbor doctrine: the rail, stage windows, and the Tasks / Notes / Files / Orch views

Part of CLAUDE.md. The single file crossed the Claude CLI's 150k-char auto-load limit on 2026-08-29, so the per-area doctrine moved here VERBATIM; nothing was rewritten. Everything below carries the same force as CLAUDE.md itself. Read this file BEFORE touching `renderer/sidebar/`, stage window chrome, unseen-completions or the taskbar badge, project icons, usage meters, the WorkflowStrip, `ViewSwitch`, the Tasks view or `bin/harbor-tasks`, the Notes view or `bin/harbor-notes`, the Files (artifacts) view, or orchestration surfaces.

- **The rail is the ONLY session browser.** The stage shows up to 16 OPEN windows (`Ctrl+1-4` switches selection among the first four, the design's core interaction); that is selection among what's open, not a second browser. Do not reintroduce workspace/tab strips or any other session-listing surface.
- **A window header keeps its IDENTITY and its CLOSE button at every grid density (2026-07-27).** At 12 windows Pat lost project names and titles entirely, and the close `×` appeared on only one window. There was no dense mode gone wrong: there was **no density handling at all**. `.wh` was one nowrap flex row in which `.who` (project + title) was the only shrinkable child, so in a ~558px cell it squeezed to zero width, the row then overflowed, and since `.tile-close` is the LAST DOM child, `.win2{overflow:hidden}` clipped it away. Nothing was keyed to selection; the window that kept its `×` was simply whichever one carried fewer chips (a fresh session with no context gauge). Fixed structurally rather than by hiding things, because his note was "theres a lot of room still for each window but honestly the ui wastes most of it": the status chips are grouped in `.wh-meta` and the controls in `.wh-ctl`, and at `data-grid-cols` 3 or 4 the header wraps so **the chips move to a second header line as a unit** while identity and controls keep the first. `data-grid-cols`/`-rows`/`-count` were already set by `Stage.jsx` and previously referenced by no CSS at all; density keys off them (focus mode forces cols=1, so a focused window gets the single-line header back). Do not solve a narrow header by letting `.who` shrink to nothing again, and verify at the real 2560x1600 geometry that every window shows project, title and a close button inside its own box.
- **WHICH SESSIONS FINISHED WHILE YOU WERE AWAY (2026-08-14).** Pat runs 12-14 open windows with 4-5 actually working, closes Harbor for a while, and on return cannot tell which sessions completed a turn and are waiting for him. `renderer/stage/unseen-completions.cjs` is the whole rule and is PURE: a session is waiting when it is not working and its transcript clock has advanced past the last time he looked at it. That formulation is chosen because **Harbor observes nothing at all while it is closed**: `notify.js` watches live work→idle transitions for toasts, in memory, and dies with the app, so nothing built on watching transitions could answer the question actually asked. Two durable timestamps can. The store (`localStorage['harbor-seen']`) is a WATERMARK plus per-session checks: the watermark is stamped ONCE on first run, which is what stops all 719 existing rail sessions lighting up the day this ships, and is also the fallback for a session with no entry, so a session STARTED later still announces itself. It holds a timestamp per session rather than a flag, because a session finishes, gets checked, runs again and must be able to mark itself a second time; re-seeding is refused for the same reason (it would silently mark everything read). Selecting a window marks it seen and keeps marking it on every update while it stays selected, so a turn completing in the window he is watching never badges. Two cues, never one: `blocked` (waiting on an answer, amber, reusing the existing needs-your-answer vocabulary) OUTRANKS `finished` (accent), because they ask different things of him and a blocked session reported as merely done is a lie he would act on. Working/blocked are read from the OPEN transcript header where there is one and from the daemon's agent status otherwise, the same preference the voice settle-watcher makes, because agent detection lags 60-150s and this is a promptness feature. `activeMs` must be the TRANSCRIPT clock and never the rail's live heartbeat: `sidebar-model` stamps `lastActiveMs = now` on every refresh for a pane with no history row, and a clock that always reads "now" would re-mark a session the instant it was checked, forever (the `isHistorical` guard is what keeps those rows out). **The marker is on the project GROUP header as well as the row**, found by driving it rather than by reasoning: the attention map was computed correctly for 723 sessions and the rail still showed nothing, because a collapsed project renders none of its session rows at all, so a group with three finished sessions read as quiet. The window-header pip sits in the IDENTITY run (never `.wh-meta`, which the density rules wrap to a second line at 3-4 columns, precisely the crowded grid this exists for) and beside the TITLE rather than the project icon, whose fallback is itself a coloured dot that made two adjacent dots read as one control. Driven end to end offscreen: a fresh seed marks 0, a backdated watermark marks 17 projects, expanding one shows its rows marked, opening a session clears its row and persists the check while the other three stay marked, and a restored two-window stage shows the pip on the unselected waiting window and none on the selected one. **The same attention map drives a Windows taskbar overlay badge (2026-08-22)**: one overlay per taskbar button is all Windows offers, so AMBER with the blocked count wins whenever any session needs an answer (blocked outranks finished, the same precedence as the pips), else ACCENT with the finished count, else cleared; counts display 1-9 then 9+, the overlay description always carries both counts in words, `stage/taskbar-badge.cjs` is the pure plan, the renderer rasterizes the bitmap on a canvas (main cannot) and sends it over `window.harbor.badge.set` debounced ~250ms, and the win32-gated main handler calls `setOverlayIcon` passively: it never focuses, flashes, or restacks anything.
- **Rail and stage state persist to `localStorage`.** The rail stores `{width, hidden, grouping}` under `harbor-rail`; the open-window stage stores `{tiles, selectedId}` under `harbor-slate-stage` and restores across reloads. Any driver/harness that opens windows must clear `harbor-slate-stage` at boot or restored windows false-match its assertions (live-caught); E2E isolates `userData` instead.
- **Project icons are USER data, and that is why the feature exists at all (2026-07-29).** The per-project image drawn wherever Harbor would otherwise draw a coloured dot (rail rows, window headers, command bar, Files, Orch picker) is read at RUNTIME from the project-icons directory (`<userData>/project-icons`, override `HARBOR_PROJECT_ICONS_DIR`, config key `paths.projectIconsDir`) and served over the `harbor-icon://` scheme, whose handler answers only for a filename its own index found in that one folder, so no renderer string ever composes a served path. It used to be a build-time `import.meta.glob` over a repo assets folder plus a `SLUG_BY_LABEL` map of 26 real project names, which made a personal icon set into repo content: the share pass (`e59c3be`) correctly deleted 53 privately-named icons and the map, and thereby deleted the whole feature, because an icon had nowhere else it could live and every surface fell back to the dot. Pat caught it as "you dropped my custom app logo / image usage". The label to filename rule is DERIVED, never mapped (`renderer/stage/project-icon-slug.cjs`): lowercase, `&` becomes `and`, spaces and separators become hyphens, so `Team Tools` is `team-tools.png` and `Notes/Wiki` is `notes-wiki.png`; a nested label also falls back to its leaf, tried LAST so a full-label icon always wins. Order is user directory, then bundled, then the dot. The bundled folder stays empty in the repo and carries a `.gitignore` so a personal set cannot be re-committed. `ProjectIcon` SUBSCRIBES (`useSyncExternalStore`) because the list arrives after first paint and the folder is watched; a URL carries the file mtime so a replaced icon repaints, and the failed-image flag is keyed by URL so a new file never inherits an old one's verdict. `providers/icon-gen.js` (2026-08-12) generates an icon for a project that has none AUTOMATICALLY (2+ sessions spanning 30+ minutes; a startup pass plus a 45-minute rerun cadence since 2026-08-22, when the prior 6-hour default made the feature read as inert for any project born mid-day; never for an orchestration worktree, the same `isOrchestrationCwd` rule the rail groups by; attempted slugs are never retried, so deleting a generated icon stays deleted), into the same watched directory. Do not reintroduce a name map, and do not resolve an icon path from a label at the main-process end.

Each window group is a **grid with identical tracks** (donut, percentage, reset) with the percentage right-aligned and the 5-hour group a fixed width, so the columns line up down all three account rows; laid out as plain inline flex they did not, because an account with no 5-hour badge pulled its weekly donut left of its neighbour's and "0%" against "66%" shifted the rest (Pat caught the raggedness on sight). Off under `HARBOR_E2E` and `HARBOR_NO_USAGE_FETCH=1`; harnesses must never hit real accounts.
- **Workflow runs render from files, and a killed run says so (2026-07-24).** Every session window carries `stage/WorkflowStrip.jsx`: a strip appears when the session has Workflow tool runs, and clicking opens the inspector (phases, per-agent rows, result previews). `main/providers/workflow-runs.js` derives ALL of it from disk because no live progress file exists anywhere: `<session-dir>/subagents/workflows/<runId>/` (journal.jsonl started/result events, agent-*.jsonl standard-schema transcripts, agent-*.meta.json models) for live runs, `<session-dir>/workflows/<runId>.json` for the authoritative completion record, and the PARENT transcript's Workflow tool_result (bounded 8MB tail scan) for a live run's name/phases via its script file. The journal carries ONLY started/result: live phase/label state exists nowhere on disk, so live rows show prompt previews, never invented labels. A run with no completion record and cold files is reported "killed mid-run" with returned counts (the OOM-kill shape), never running, never quietly done. IPC `session:workflow-runs`, 4s renderer poll, no poll for `pane:`/`live:` provisional ids.

One row at EVERY width down to the 190px minimum, measured in the drive (`scripts/drive-viewswitch-win.js`, port 9339), not estimated; `scripts/drive-artifacts-win.js` selects tabs by aria-label now, never by label text, because inactive tabs draw no text. - **The Notes view is where drafts leave Harbor formatted, not mangled (2026-08-25, task t_mt8yupnk58nvkmx).** Pat's verbatim pain: Claude-drafted Teams/Outlook replies arrive in "terminal formatting", pasting loses bullets and the blank lines between paragraphs, and he spent 5-10 minutes per draft undoing "bootleg bullet points". The note body is edited WYSIWYG by REUSING `stage/ComposeEditor.jsx` with one opt-out prop (`submitOnEnter={false}`, so Enter makes paragraphs instead of sending); there is no second serializer anywhere.
- **The Tasks view is the one surface that is purely the user's own (2026-07-30).** Pat asked for "something similar to the basic Microsoft to-do" inside Harbor, because Obsidian's task pipeline derived and rewrote tasks on its own and stopped being trustworthy. So: `renderer/tasks/TasksView.jsx` (list nav + rows + quick-add), `renderer/tasks/TaskEditor.jsx` (the modal Pat asked for, every field plus created/modified/completed metadata), `renderer/tasks/use-tasks.js` (the doc + a `useToday` that wakes exactly at the day roll instead of polling). `shared/tasks-model.cjs` is the WHOLE brain: a pure reducer (`applyOp`) plus pure selectors (`selectRows`, `counts`, `tagIndex`), and BOTH ends apply the same reducer to the same document, so a mutation cannot mean one thing on disk and another on screen. `main/providers/tasks.js` owns the file: atomic tmp+rename, a `.bak` of the copy it is replacing, and unreadable JSON is quarantined as `tasks.json.corrupt-<ts>` and reported, NEVER overwritten. Decisions that are load-bearing: a "day" is a LOCAL `YYYY-MM-DD` key rolling at **6am** (`date-roll`'s `DAY_ROLL_HOUR`, reused rather than re-declared) so a UTC or midnight roll cannot empty My Day mid-evening; **My Day is a date stamp, not a flag**, which gives Microsoft's daily reset with no background job; completing a parent cascades to its subtree stamped with `completedBy`, so unticking restores EXACTLY the children that cascade closed and never one finished on its own; `normalizeDoc` is TOTAL and repairs the parent graph (missing parents, cycles, cross-list parents, over-deep branches flatten onto the deepest legal ancestor) because a hand-editable file means "half of it is nonsense" is an ordinary input; and the seeded list's id is FIXED (`list-default`), not generated, because a generated seed id differs on every read and a fresh install renaming its own starter list was refused as "that list no longer exists" (live-caught while driving the app). The task column is CAPPED at 1060px and CENTRED: measured at 2560x1600, full-width rows put the star a screen's travel from its title and a left-aligned cap left 880px of empty card. Do NOT add a per-row "My Day" flag back at the right edge; the ☀ rendered as a near-twin of the ★ and it reads as a bug (it is metadata beside the due date now). **A star PINS its task to the top (Pat, 2026-08-02).** `starFirst` is the first key of My order everywhere the default order is used (a list's tree, among each task's OWN siblings so a starred sub-task rises without leaving its parent; a smart view's flat run, above the by-list grouping, because a star buried at the head of the third list is the same thing as no star; the Completed section; and the CLI, which reads through the same selector). It deliberately does NOT override an EXPLICIT sort, since answering "sort by due date" with three undated starred tasks on top is the app arguing with an instruction, and it made the old `importance` sort a second name for the default, so that option is GONE rather than sitting in the menu doing nothing (a saved `'importance'` falls back to manual, which is what it now means). The pin also splits screen order from stored order, which manual reorder has to translate between: `renderer/tasks/reorder-move.cjs` (`planMove`) resolves an Alt+arrow against the VISIBLE neighbour (a blind ±1 in order-space steps past a row that is elsewhere on screen and reads as nothing happening) and refuses any move ACROSS the pin, because "before C" in stored order is not "above C" on screen and accepting it moved the row the OPPOSITE way. **Assign to Claude (2026-08-22)**: every task row and the editor carry an Assign action opening a portal modal (task summary + OPTIONAL folder/account/model/effort/instructions, defaults from the saved new-session default, never a hardcoded model) with two launches: Assign (chosen config) and YOLO (all defaults, cwd `C:\dev`, the prompt tells the agent to locate the right project first). The composed prompt is a pure module (`renderer/tasks/assign-to-claude.cjs`): task facts + verbatim instructions + implement-fully/verify + completion via `harbor-tasks done <task-id>` BY ID never title (sanctioned because Pat clicked Assign) + a no-other-tasks prohibition. The initial prompt rides the existing launch chain to `bin/ai`'s positional PROMPT; a successful launch appends one assignment line (session id + timestamp) to the task note via the reducer (`task.appendAssignment`), and a refused launch surfaces in the modal and appends nothing. **The list-color hex field is a DRAFT while focused (2026-08-22)**: it used to commit every valid partial (a 3-digit hex is valid) and the parent's normalized echo rewrote the field mid-type, which Pat experienced as unwanted autocomplete; `renderer/tasks/color-picker-hex.cjs` now gates prop sync on focus and settles on blur/Enter only, while swatches and the hue slider still commit instantly. **A task DUPLICATES whole (2026-08-25, task t_mt8ytlxf4asz2pd)**: `task.duplicate` in the reducer deep-copies the task AND its subtree with fresh ids and remapped parents, keeps the facts (title, notes, dueDate, tags, star, My Day, list, parent), opens EVERY copied node (done/completedAt/completedBy reset, because a duplicate is new work), and lands the copy immediately after the original among its siblings; the row's hover cluster and the editor both carry a Duplicate action, and both OPEN THE EDITOR ON THE COPY so "change the text, keep the rest" is one click plus typing; `harbor-tasks duplicate <id|title>` rides the same op.
- **Agents drive the task list through `bin/harbor-tasks`, ON REQUEST ONLY (Pat, 2026-07-30).** The CLI is the same document, the same reducer and the same writer the app uses; there is no second implementation of what a task means, and `shared/tasks-file.cjs` holds the ONE path rule both ends resolve (`HARBOR_TASKS_FILE` → `paths.tasksFile` → `<userData>/tasks.json`, with the CLI deriving userData per platform since it has no Electron; the shared win32 config home is `~/.harbor`, see Machine and shared state in the root CLAUDE.md). Because Harbor is no longer the only writer, `mutate` takes a CROSS-PROCESS lock (an atomic `mkdir` on `tasks.json.lock`, stale after 15s, best-effort so it can never refuse to save) around the whole read-modify-write, and the store's fs.watch pushes an outside edit into the open window without a reload (proven end to end by E2E spec 19, which drives the real CLI as a separate process against the file the app is showing, both directions). A task is addressable by id OR by a unique piece of its title, and an ambiguous phrase is an ERROR listing the candidates: a fuzzy match that picks one is how the wrong thing gets deleted. The `harbor-tasks` skill in `~/.claude/skills/` (junctioned into all three config homes) carries the constraint that makes this safe and is the reason the list left Obsidian: **never add, complete, re-tag or delete a task on its own initiative.** Artifacts discovery is TRANSCRIPT-driven (`main/providers/artifacts.js`), never a filesystem sweep: a file counts when a recent transcript names it (Write file_path, Bash command, tool result; raw regex per line, base64-immune because '.' is not in the base64 alphabet), it has a viewable extension, it exists, and its mtime is not older than the naming session's start (a session that READ an old image never claims it). Excluded: node_modules, .git, dist, caches, config homes, scratchpads. Cache at `~/.cache/harbor/artifacts-index.json` (cold corpus scan ~77s once, ~40ms warm, background-warmed at boot); env: `HARBOR_ARTIFACTS_ROOTS`, `HARBOR_ARTIFACTS_CACHE`. EVERYTHING renders inline (Pat mandate 2026-07-25: never "open externally" as the primary path): HTML in an iframe sandboxed `allow-scripts`, images in `<img>`, PDFs via Chromium's built-in PDF viewer (`webPreferences.plugins: true`; that frame is deliberately UNsandboxed because a sandboxed frame gets no plugins), video in `<video>`. Every grid card also PREVIEWS (Pat, same day): `providers/artifact-thumbs.js` generates on-demand, serialized, disk-cached thumbnails (`~/.cache/harbor/artifact-thumbs`, env `HARBOR_ARTIFACT_THUMBS_DIR`) via an offscreen Electron capture for HTML (loaded through the same scheme, same no-navigation posture), `pdftoppm` first page for PDFs, `ffmpeg` first frame for video; a missing tool degrades to the glyph, never an error, and generators only ever run on indexed artifacts. Main cancels http(s) AND file SUBFRAME documents, so no artifact frame, sandboxed or not, can become a browser or local-file reader; will-navigate refusal and window-open denial stand. Open-externally/show-in-folder remain as secondary header actions through guarded IPC (`artifacts:open-external` checks the allowlist). Do not add a per-cwd extension sweep, do not loosen the scheme allowlist or the subframe blocks, and do not sandbox the PDF frame (that silently turns render into download). **The whole view was POSIX-ONLY, and on Windows it served nothing at all (2026-08-13).** Pat's screenshot: broken-image icons on every png, glyph placeholders on every HTML and PDF, and clicking a card opening a viewer with nothing in it. Three separate POSIX assumptions in one pipeline, each invisible on Linux. (1) `artifactUrl` built the URL as `//local${p.split('/').map(encodeURIComponent).join('/')}`: a drive-lettered path contains no forward slash, so it stayed ONE segment, the entire path was percent-encoded into the URL's **HOST**, and `url.pathname` came back `''`; the handler resolved `'.'` and refused. (2) `isServable` compared a `path.normalize`d candidate (`\dev\x.png`) against a set holding the raw extracted spelling (`/dev/x.png`), so it answered false for **every** artifact: the scheme 403'd everything AND `artifacts:thumb` refused before generating, which is why the thumbnail cache directory did not exist at all. (3) The extraction regexes matched only `/`-rooted paths, so `Write`'s `file_path`, the primary signal this module is built on, was invisible on Windows; the few artifacts that did appear were an accident of Node resolving a leading `/` against the current drive, which is also why they were stored drive-less and disagreed with every consumer. Measured on the real 14-day corpus: POSIX-only extraction found 72 files that exist on disk, drive-lettered shapes found 610. The fixes: `shared/artifact-url.{js,cjs}` is now the ONE rule for a path inside a `harbor-artifact://` URL and back, PLATFORM-PURE (it keys off the drive-letter SHAPE, never `process.platform`) and carrying the path in the URL PATH with real `/` separators, because an HTML artifact's relative `./chart.png` has to resolve to its real sibling; **never rebuild this by splitting a native path on `/`**. `canonicalPath` (`path.resolve`) is applied at index time AND in `isServable`, so the two spellings of one file collapse to one artifact and the allowlist cannot disagree with the index; `isExcluded` compares in the `/` spelling so one rule covers both separators, and the session-scratchpad exclusion gained its Windows spelling (`<temp>/claude/<project>/<session>/scratchpad/`, the same rule as the POSIX `/tmp/claude-` prefix, worth ~260 throwaway probe renders that would otherwise crowd real work out of the 500-artifact cap). The artifacts cache carries `CACHE_VERSION`, bumped whenever `extractCandidates` changes: the cache is keyed by transcript size+mtime, so without a bump a new extraction rule applies only to sessions written after it shipped and the fix looks inert on exactly the history being viewed. Verified from the consumer end, not from reasoning: a real Electron run fetched every indexed artifact through the real handler for **249 clean 200s, zero refusals** (before: every one refused), and html/pdf/video thumbnails generate and serve. **The gate could not have caught any of it, and that is the part that got fixed rather than noted.** The e2e suite already asserted `naturalWidth > 0` on image/html/pdf cards and passed throughout, because it is Linux-only by construction and cannot be pointed at win32; so "the gate will catch it next time" is false for every platform-shaped bug in this pipeline. The serve decision therefore no longer asks the HOST for its path flavour: `createServeAllowlist(pathImpl = path)` takes it as an argument, production passes the native `path`, and `test/providers/artifacts.test.js` drives the SAME assertions through `path.win32` and `path.posix` on whatever machine runs them. Reconstructing the old rule under the win32 flavour refuses the indexed artifact, its native spelling, its URL round-trip spelling and its siblings, all four, so those specs fail against it from any runner. This is the same correction `project-label.cjs` got on 2026-08-12 after posix-only specs lied on a Windows host: **when a rule is platform-shaped, parameterise the platform and assert both, because the only gate cannot travel.** **A pending composer attachment is clickable (same day).** The chip's only control was its `×`, so the one thing a click could do was destroy the image ("clicking on it does nothing (unless you click the 'x')"). The thumbnail is now a button that opens `stage/ImagePreview.jsx` (portalled to `document.body` like every other overlay, because a `backdrop-filter` ancestor would trap it); `attachmentPreviewPlan` in `command-bar-attachments.cjs` owns the decision, so it has a test rather than living in JSX: a pasted or dropped image previews from the data URI it already carries, and one without bytes (the Electron-clipboard path, and any draft restored from `localStorage`, which persists paths and not bytes) is read back through `clipboard:image-data-uri`, a LOCAL-ONLY channel bounded to the paste cache directory.
