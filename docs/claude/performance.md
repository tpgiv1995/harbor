# Performance doctrine: what Harbor spends per open window, per session and per refresh

Load before touching any timer, poll, cache, whole-file read, per-chunk work or cross-process copy in Harbor (main, renderer, phone server, sessiond, keepers). Every rule here came from a live measurement on 2026-11-06, when Pat reported that Harbor with ten sessions "destroys the computer" while ten sessions in a terminal do not. Harbor's own CPU was then about 64% of a core and the phone server alone held 1.2 to 2.3 GB. The causes were not animations; they were steady-state work multiplied by windows, sessions and processes. The run record is `docs/orchestration/2026-11-06-harbor-perf/`.

- **Multiply before you add.** Harbor runs the rail pipeline twice (desktop main and the phone server, `server/compose.js`), up to 16 open windows, and one keeper per session. A "cheap" 5 s poll per window is 32 reads every 5 s across two processes; a 1 MB read per poll is a gigabyte an hour. State the per-window, per-session and per-process cost of any new periodic work in its comment, and measure it on Pat's real corpus (12,000 transcripts, a 17 MB index cache, transcripts up to 352 MB), never on a fixture alone.
- **A poll's dependencies are IDs, never objects (2026-11-06).** `AskCard.jsx` listed the `pane` object in its poll effect's deps; every sidebar model (about two a second) handed it a new object for the same pane, which cancelled the 700 ms timer and polled at once. Each open Claude window drove about 24 screen reads a second through main, the daemon and its keeper. The poll reads the pane through a ref and re-arms on `paneId`. Pinned by `test/renderer/session-tile-ask.test.js`.
- **One menu poll reads each screen view once (2026-11-06).** `getMenu` walked readMenu, readFallback and readList, five or six daemon round trips for one question (7,434 screen reads a minute from six windows, 719 MB a minute of daemon allocations). `session-send.js` shares reads inside one `getMenu` call through an AsyncLocalStorage store, and any input it sends (`sendPaneInput`) ends the sharing, so a walk that types and re-reads sees the redraw. Input from ANY caller bumps the pane's generation and ends sharing in every poll that has read that pane (two polls can await one discovery walk whose keys the first one sends; Astra review). Outside a menu poll nothing is shared. Pinned by `test/main/menu-poll-reads.test.js` and the walk tests in `test/main/ask-sheet-delivery.test.js`.
- **The pending-question read scans only appended bytes (2026-11-06).** `providers/pending-ask.js` re-read the 1 MB transcript tail on every change, and a working session changes every second: 8 MB read to notice 6 KB of new lines. With no question open, only an appended line naming `"AskUserQuestion"` can change the answer (an older question's answer comes after it), so the appended complete lines are searched as bytes without decoding; a hit, an open question or a rewrite takes the full tail read. Growth alone is not proof of an append: the file identity (bigint dev and ino), the first 256 bytes and the 256 before the last stop must all be unchanged, or the file is read whole (Astra review, two rounds). Pinned two-sided in `test/main/pending-ask.test.js` (counted at `fs.readSync`).
- **The rail's session list crosses as changed rows only (2026-11-06).** Every history refresh shipped all 12,000 rows as a 14.8 MB string across the worker boundary and parsed it on the main thread, in both processes, about three times a minute (61% of the phone server's allocations). `history-index.js` `emitDelta` answers a caller holding its last cursor with the id order plus only the lines that changed; `history.js` parses each changed line from its own small string (so no row pins a 15 MB parent string) and reuses the rest. Any other cursor gets every line. Measured on the real list: 85 to 92 MB and 3.6 to 4.5 s per refresh before, about 5 MB and 0.35 s after. `parseEmitLine` also stopped spreading each prompt into a character array (`codePointSlice` counts code points in place). Pinned by `test/providers/history-list-delta.test.js`.
- **The index cache has one writer and is not rewritten every pass (2026-11-06).** `index.json` (17 MB) was stringified and rewritten whole on every pass that saw one transcript grow, every 10 to 30 s, by the app and again by the phone server. Every entry is re-checked against its file, so a stale cache costs re-parsing, not wrong rows; but the titler reads this file from disk, so it is not only a cold-start aid. The app writes at most every 2 minutes (`saveIntervalMs`, newest pass, trailing timer, flushed on close) and a late write announces itself (`onPersisted` -> `history-changed`, one more refresh) so a new session is still named; the phone server runs `indexReadOnly`; a one-shot CLI keeps writing every pass. Pinned two-sided by `test/providers/history-index-save-interval.test.js`.
- **The home map reads each home's inputs only as far as they changed (2026-11-06).** Any prompt appends to its home's `history.jsonl`, and `buildHomeMap` re-parsed all seven homes' files (4.2 MB) and re-listed about 19,000 session-env and file-history names on almost every refresh, in both processes. Per home, a grown history file is now read from its last complete line (the unfinished tail is re-read each time, exactly as a whole read sees it) and a folder is re-listed only when its stamp changed; a shorter file, a changed first 256 bytes, another file identity or a same-size file whose mtime moved is read whole, and a folder that fails to list (anything but ENOENT) keeps its last good answer and is retried rather than cached as empty. Pinned by `test/providers/history-home-map-incremental.test.js` (equal to a fresh whole read through appends, half-written lines, U+2028 inside a prompt, rewrites, new folders, deletion; old code fails the cost test).
- **The Codex/Cursor facts cache is written at most every 2 minutes (2026-11-06).** Any live codex session grows its log, so every refresh restringified and rewrote the whole 4 MB `provider-row-facts.json` in both processes. `provider-history.js` now writes on a trailing timer (`factsSaveIntervalMs`) and flushes on close, with write generations so an older write that lands late can never be the last word, and memoizes the cwd munge it ran over thousands of known cwds per refresh. Pinned by `test/providers/startup-scan-caches.test.js`.
- **Only rows the delegation scan can use cross to its worker (2026-11-06).** `delegations.js` copied all ~14,000 rail rows to the worker on every refresh, which skips everything but codex rows and Claude rows live or active in the last 48 hours; a session that goes live between history refreshes re-sends the rows. Pinned by `test/providers/delegations.test.js`.
- **The titler does not re-read the index for nothing (2026-11-06).** A pass ran after every history refresh and parsed the 17 MB index on the main thread before learning that no session needed a name. `titles.js` skips a pass whose index and titles files are unchanged since a pass with no candidates, for at most 10 minutes. Pinned by `test/providers/titles.test.js`.
- **A keeper models only the scrollback a reader can ask for (2026-11-06).** `daemon/screen.js` kept 10,000 lines per session while the largest read is 200 (and the daemon caps any read at 1,000): measured 53 to 194 MB committed per keeper against about 46 MB bare. `MODELED_SCROLLBACK_LINES` is 2,000; raise it only together with a reader that asks for more. `keeper.js` builds the base64 frame copy only when an observer is attached. Both apply to keepers spawned after a deploy; a running keeper keeps what it has.
- **One `list` poll per daemon per process (2026-11-06).** Three subscriptions in the app and two in the phone server each polled the daemon's `list` every second (266 requests a minute). `session-daemon/client.js` `SharedSnapshotPoller` makes one fetch per tick and fans it out; each subscription still diffs against its own previous panes. A subscription with its own `pollIntervalMs` keeps its own timer. A tick serves only the members present when it started whose client was healthy then (one that joined mid-fetch may hold a newer seed, and an older answer reported its new panes closed), the shared fetch never overlaps itself, and a client whose last fetch failed is retried on its own, one request at a time, with its members getting only its answers or errors, so a slow broken client never holds up the healthy ones (Astra review, two rounds). Pinned by `test/main/session-subscription-shared-poll.test.js`.
- **Transcript windows (2026-11-06, `providers/transcript.js`).** The image store cap is 128 MB per process (`image-store.js`; measured working set 104 MB across the 14 largest recent transcripts), and images of blocks that are trimmed right away (the skipped-prefix scan, paging chunks) are never hashed or stored (`applyLineDeferred` / `commitImageRef`). The skipped-prefix scan is cached (16 entries, one per window the stage can restore, 24 MB) and resumed when the file only grew (`getPrefixSeed`; reopening the 352 MB transcript went from 1.4 s to 11 ms). Reuse rests on transcripts being append-only JSONL: the check is the file identity, a same-size file whose mtime moved since it was LAST seen (the stamp moves forward on every validated reuse), and hashes of the first, last and six interior 4 KB of the covered range. That catches rewrites in practice but is not a proof; a rewrite leaving every sampled range identical is not detected. The opening prompt's pictures are settled even when the parser has trimmed the opening away, and a seed never replaces the opening's servable pictures with ones the store cannot serve (Astra review). The 5 s per-window poll sends nothing when no block changed and the header is identical (`emitUpdate` `onlyIfChanged`; a header that changes only with the clock still goes out), the statusline tee is re-parsed only when its file changes, and the liveness beacon is re-read at most every 30 s (it feeds the status light's 10-minute rule, not adopt-on-send). Pinned by `test/providers/transcript-perf.test.js`.
- **Measured result on the phone server (2026-11-06, same code as the desktop rail).** Allocations over 60 s: 1,817 MB with the old code after 8 hours up, 481 MB with the first batch of these fixes (history list 1.2 GB of it before, 27 MB after). Commit 1.30 GB before, 0.78 GB a few minutes after the restart.
- **The question card's transcript lookup scans the whole store at most every 30 s per session (2026-11-06, Astra review).** `ask-transcript-path.js` ran the 4,486-folder scan on every 700 ms poll of a session with no transcript yet (13,458 access attempts in three polls). Cheap derived-path and cwd checks still run every poll. Pinned by `test/main/ask-transcript-path.test.js`.
- **How to measure without touching live work.** The phone server, sessiond and keepers are plain `node.exe`: `process._debugProcess(<pid>)` opens their inspector on 9229, and a HeapProfiler sampling profile with `includeObjectsCollectedByMajorGC`/`MinorGC` gives allocations per call site over a window; a conditional breakpoint whose condition counts and returns false counts calls (verbs per minute) without pausing. The Electron main cannot be attached live (`OpenFileMappingW` fails), so its costs are measured through the same code in the phone server, or at a restart with `--inspect`. Never run `npm test` while sampling: the suites spawn daemons and skew every number. Process CPU and commit come from `NtQuerySystemInformation` snapshots a few seconds apart.
