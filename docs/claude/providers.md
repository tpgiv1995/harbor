# Harbor doctrine: launches, providers, config homes, and the bin/ organs

Part of CLAUDE.md. The single file crossed the Claude CLI's 150k-char auto-load limit on 2026-08-29, so the per-area doctrine moved here VERBATIM; nothing was rewritten. Everything below carries the same force as CLAUDE.md itself. Read this file BEFORE touching launch actions (`actions/launch.js`, `bin/ai`, `bin/claude-sessions`), `NewSessionConfig` and the new-session flow, `main/config/homes.js`, `providers/capabilities.js` / `model-catalog.js` / `titles.js` / `provider-history.js`, or codex/cursor support.

**New-session config flow**: every launch entry point (rail head `+P`/`+T`, per-project hover actions, stage dashed slots, app menu, the `--new-session` second-instance chord) walks a folder picker then opens `NewSessionConfig` (portal popover: account, **provider**, model, effort, folder). IPC: `new-session:options` (provider registry from `capabilities.newSessionOptions()`), `new-session:folder`, `new-session` → `launchNewSession` → `bin/ai`. **A CLAUDE session has no provisional phase at all (2026-08-04): Harbor MINTS its id.** `claude --session-id <uuid>` takes the id from the caller (verified end to end: a minted id produced its transcript at exactly that path), so `bin/ai` forwards it, `launchActions.newSession` mints with `randomUUID` and returns it, and the new-session window opens on that real id from first paint. Harbor never has to DISCOVER which session a claude pane holds, which is what the 2026-07-27 lost-draft and both 2026-08-02 second-session incidents were made of. It is claude-only on purpose: **codex offers resume and fork BY id and no way to choose one at launch**, so everything below still applies to it verbatim. A fresh CODEX pane opens as a provisional `pane:<id>` window and the real session id upgrades the tile once the first message materializes the rollout. **That upgrade is driven by the DAEMON's pane-to-session pairing, not only by the launch that opened the window (2026-07-28).** The launch flow watches for a fresh transcript for 45 seconds and then gives up, which looked exactly like lost work: Pat spent twenty minutes composing into a fresh window, and by the time he pressed Enter nobody was watching. The send landed, a real session started and Claude went to work, but the window kept its provisional id, and provisional ids are excluded from transcript subscriptions, so it sat on "Fresh session. Type below to start it." while his 2,137 characters ran out of sight. `renderer/stage/provisional-upgrade.cjs` (`planProvisionalUpgrades`, called from the stage effect on every model update) adopts the real id from the sidebar model's own pane-to-session pairing, so there is no timeout to outlive and a window already sitting wrong heals on the next update. It is deliberately RENDERER-side: the first version announced the pairing from main over IPC, which fired once before the renderer had restored its stage and then never again, and the window stayed wrong exactly as before. Upgrading onto an id that ALREADY has a window collapses the duplicate rather than leaving two windows on one session. Default is **opus + xhigh** (the model ALIAS, never a pinned id), unified across the rail's one-click P/T/S and the popover, with a one-time re-seed of the saved default (`NEW_SESSION_DEFAULT_VERSION`). **A PROVISIONAL WINDOW IS A SESSION: its config APPLIES, it does not launch (2026-08-02).** The popover's one real decision (change this session, or start a new one) has now cost Pat a session he did not ask for twice, and it lives in `renderer/session-config-mode.cjs` (`isReconfigure`, `pendingSwitch`) so the rule has a test instead of a screenshot: 2026-07-20 gated on a live drivable pane, so changing an outside session's model launched a replacement; 2026-08-02 gated on the id not being provisional, so changing the model of a session started seconds earlier opened a SECOND window and a second session in the same project ("instead of what it should do which is just update the current one"). A `pane:<id>` window is not "no session yet": Claude Code writes no transcript until the first message, so the pane IS its identity, and `session.send` already addresses it that way. Only a provisional id with NO pane still launches, because there is nothing to type into and no id to resume from. The same fix taught the popover to read its baseline from the LAUNCH config when there is no transcript header (`currentModel`/`currentEffort`), since falling through to a hardcoded `opus` made "switch a sonnet session to opus" a silent no-op. **And the chip says what it was launched with (same day, "i cant even see what model im in for these new sessions").** With no transcript the model chip had nothing to read and drew the bare provider label, for as long as the session stayed quiet. `renderer/stage/launch-meta.cjs` keeps the launch facts alive: `mergeLaunchMeta` folds each `session:launched` payload into what is already known, because the daemon's pane-to-session pairing event carries NO model or effort and can arrive first, and replacing the record wholesale dropped the launch config exactly when it was the only description the window had; `withLaunchFacts` FILLS a session row (never overwrites: a session reconfigured after launch reports its own truth). The alias renders through the new-session registry's own label (`opus` → "Opus 5"), so the chip and the popover cannot disagree, and `model: 'default'` stays honestly unnamed. Gate spec 20 drives the whole thing against a real pty: the button reads Apply, `/model sonnet` lands in the fresh session's own pane, and no `bin/ai` launch is recorded. **A launch refusal reaches the popover (2026-08-13)**: `new-session` stats the cwd and refuses a dead or foreign folder by name (live-caught 2026-08-12: a migrated Linux-era session's `/home/you/...` cwd), `new-session:folder` answers null for one, and `NewSessionConfig` renders the error (`.config-launch-error`) instead of closing over a launch that never happened.

**Effort is applied AT LAUNCH, and the id upgrade never eats a draft (2026-07-27).** Two separate bugs Pat experienced as one ("it lags 5-10 seconds then sends the effort message and deletes what i have typed"). First: `bin/ai` parsed `--effort` and its **claude branch silently dropped it** (only codex consumed it), so the only way left to apply effort was for `main/index.js` to type `/effort <level>` into the pane once `waitForClaudeReady` settled. That cost the 5-10s pause, spent a turn, rail-titled sessions "/effort", and put a command in the transcript Pat never typed. The claude CLI has taken `--effort low|medium|high|xhigh|max` as a launch flag all along, so bin/ai forwards it and the post-boot send is gone (`test/bin/ai-launch-argv.test.js` proves the argv AND that the installed binary advertises the flag; `HARBOR_AI_DRY_RUN=1` prints the composed command). Second, and the actual cause of the lost text: **drafts key to the session id**, and a new session's id upgrades from `pane:<id>` to the real id when the transcript materializes, which orphaned the draft, so the composer read the new id, found nothing, and rebuilt itself blank. `renamedDraftStore` (both draft-store twins) moves it on the `replacesKey` swap and never clobbers a draft already under the destination. Removing the `/effort` send alone would NOT have fixed this: it only removed one trigger for the upgrade, and his first real message would have done the same. Spec 6h drives the real event and is proven two-sided.

**Provider registry**: `main/providers/capabilities.js` `newSessionOptions()` is the source of truth for launch-time provider/model/effort choices (claude, codex, cursor). `renderer/providers.js` maps each key to label, accent color, and SVG logo for the rail (`.sr-provider`), conversation who-row (`.conv-sig`), command-bar model chip, and new-session popover. Non-Claude providers skip the account suffix in the who-row.

`bin/` holds the reusable "organs": `claude-sessions` (fzf picker, backed by the Node history index; symlink it as `hist` yourself if you want it on PATH), `harbor-sessiond` (the daemon lifecycle CLI: start/status/list/kill/logs/spawn; the ONLY sanctioned daemon starter, see `docs/claude/sessiond.md`), `harbor-tasks` (the Tasks CLI, see `docs/claude/views.md`), `ai` (new-session launcher; `--home <profile|config-home>`, `--provider claude|codex|cursor`, `--model`, `--effort`, `--session-id`, an optional positional PROMPT, and `--here` to stay in the current pane; it execs the provider CLI itself, resolving each binary from `providers.<id>.bin` then `HARBOR_<ID>_BIN` then PATH, and pre-accepts the per-folder trust marker in the config home the child will read, in BOTH path spellings since CLI 2.1.229 respelled its project keys with forward slashes, 2026-08-13), and `harbor-bin.cjs` (the shared policy/argv library behind them, home of `resolveUnitPolicy` and `cleanDaemonEnv`). `providers/titles.js` caches Haiku session titles to `~/.cache/harbor/session-titles.json`, reads its key from `~/.config/harbor/titler.env`, and NEVER titles `BATCH TITLE:` workers. The background scheduler preserves `HARBOR_NO_TITLER`/`HARBOR_TITLER_FORCE`/`HARBOR_TITLER_DELAY_MS`. A session with no head-scan first prompt is still a candidate when its opening command is real, while settings-only sessions stay honestly untitled; **a session is named TWICE** (2026-08-12): the first title knows only the opening line, so once the session has gone somewhere (`MATURE_DEPTH`) it is re-minted once and then left alone. The retired Python indexer and titler survive only as equivalence oracles under `reference/python-oracles/`; no product path runs them.

- **The titler NEVER titles its own children, and a title call leaves NO transcript behind (2026-08-24).** Since `bf8742e` a title is minted by spawning `claude -p` (so it bills the plan, not a stray API key), and that child is a REAL session whose transcript lands in the very `~/.claude/projects` dir the titler scans. Its opening prompt is the titler's own `SYSTEM` instruction, which the `BATCH TITLE:` skip never matched, so the titler titled its own output and each title spawned another: **4,854 identical junk sessions in seven hours** before it was caught, the rail's HARBOR/APP group flooded with "You name terminal coding…" rows and Pat's plan burning a Haiku call every few seconds. A raw HTTP title (pre-`bf8742e`) wrote no transcript, which is why this could not happen before and why the CLI spawn is exactly what reintroduced it. Two guards, both in `titles.js`, overlapping ON PURPOSE. The LOOP fix: candidate selection skips any session whose opening prompt starts with `TITLER_CHILD_SIGNATURE` (the `SYSTEM` opening), the same posture as the `CHILD_TASK_PREFIX` worker skip. The BLOAT fix: `runClaudeTitle` MINTS the child's `--session-id`, so `discardTitleTranscript` deletes the one transcript the call wrote the instant the title (which comes from stdout, never the transcript) is captured, keyed by the unique id so no cwd-munge has to be reconstructed. Both are needed because the `history-index.js` fs-watch can index the child in the ~5s before the delete lands, and a title caught in that window must still never be re-titled. Verified end to end against a real `claude -p` call: the title is produced, one transcript appears at `<projects>/<munged cwd>/<id>.jsonl`, and it is gone before the function returns. Do NOT re-widen the candidate scan to include the titler's own children, and do NOT drop the `--session-id`/discard pair back to letting the CLI auto-name the session.
- **Config homes are DISCOVERED, and each one is a plan.** A config home is a directory holding an account's `.claude.json`: `~/.claude` by convention, plus any `~/.claude-<suffix>`. `app/src/main/config/homes.js` scans for them and derives a profile per home (id from the directory suffix, `personal` for the bare `.claude`), which is what the migration, the setup wizard, the rail badges and the session index all read, so none of them can disagree about what a plan is. There is NO built-in list of accounts anywhere, and there must never be one again: the shipped source once carried a literal three-home list, the third of which named a real person and a directory only one machine had, and on 2026-07-29 a misfiring prior-install guard handed that whole account list to somebody else. A per-home `projects` directory may junction to another home's, which is how several accounts share one transcript history. The rail's per-project hover renders one launch button per configured profile (fixed `opus` alias + xhigh defaults; the ALIAS, not a pinned id, so the CLI resolves the current flagship and a new Opus release needs no Harbor change), and resume carries the session's own home verbatim: `resolveResumeHome` keeps whatever id the profile has, so `bin/claude-sessions --resume-id ... --home <home>` routes to the right config home. An account travels as its config home (`--home <path>` becomes `CLAUDE_CONFIG_DIR` on the child), never as a per-account flag.
- **The Claude model list is DISCOVERED, never hand-pinned (2026-07-24, built the day Opus 5 shipped and Harbor's pinned list missed it).** `main/providers/model-catalog.js` scans the installed Claude CLI binary (the consumer that actually accepts model ids) for dateless first-party ids, cached to `~/.cache/harbor/claude-models.json` keyed by binary path+size+mtime (275MB scan ≈ 350ms cold, ~3ms warm), refreshed at boot + every 6h; ids newer than the shipped seed's family flagship raise a toast once. `MODEL_VERSION_SEED` in `capabilities.js` is the FLOOR the menus can never fall below (discovery only ADDS; a failed or empty scan leaves the seed standing), labels derive from the id (`claude-opus-6` would render "Opus 6" with zero code changes), and mythos is deliberately excluded (Glasswing-only, a dead menu row here). Env: `HARBOR_CLAUDE_BIN` exact pin, `HARBOR_MODEL_CACHE_FILE`, `HARBOR_NO_MODEL_DISCOVERY=1` (also off under `HARBOR_E2E`). Do NOT add model ids by hand-editing menus elsewhere; bump the seed and let discovery do the rest.
- **Provider identity and homes are PROVIDER-SCOPED (2026-08-30, the provider-keeper work; the daemon-side half lives in `docs/claude/sessiond.md`).** A CLAUDE config home is never forwarded to a codex or cursor launch: `resolveProviderProfile` resolves the account per provider, `bin/ai` exports a codex profile's configHome as the child's `CODEX_HOME` (never `CLAUDE_CONFIG_DIR`), and no cursor home variable is invented because the cursor CLI documents none. Provider history scans every configured codex home, and a durable id-to-cwd metadata sidecar makes a dormant CURSOR session resumable across app restarts (cursor transcripts record no reversible cwd; the sidecar is written while the pane is live, which is the only time the cwd is known). The linker annotates the KEEPER when it pairs a pane to a provider session (the daemon's own state file learns the identity; see the annotate verb in sessiond.md), so the rail, dormancy, and resume all read one truth instead of an app-side overlay.
- **Codex/cursor sessions are first-class rail citizens with designed conversation windows (2026-07-24).** `provider-history.js` rows give them identity (so restored tiles survive restarts and old sessions reopen as `.conv-*` windows; verified against the full corpus: 176/176 codex + 132/132 cursor files parse), `paneProvider` in the sidebar-model twins maps the daemon's detected `pane.agent` ('codex', 'cursor', 'cursor-agent') to the provider so live panes stop masquerading as claude, and an agent pane with NO reported session id still lists under its `live:` key (the rail is the only browser; an invisible running agent is a dead end). DEAD codex/cursor sessions resume-on-send like claude (2026-07-24, driven end to end for both providers): `bin/ai --resume-id` composes `codex resume --dangerously-bypass-approvals-and-sandbox <id>` / `cursor-agent --force --resume <id>`, `launchActions.resumeProviderSession` runs it in the session's own cwd (refusing honestly when that folder was deleted; execFile's ENOENT otherwise blames the binary), and `runSend`/the `resume-session` IPC route by provider so a claude resume is NEVER fired at a foreign id. Readiness is settlement-based (`waitForProviderReady`: two identical non-empty reads, non-shell tail), not claude's composer glyphs. The only read-only case left is a cursor session whose cwd could not be un-munged (their transcripts never record one); the raw-terminal fallback remains ONLY for a live non-claude pane whose transcript is undiscoverable. **A codex rollout's session_meta line has NO size Harbor controls (2026-08-08).** Codex 0.147.0 ships the entire system prompt inside it (`payload.base_instructions`; a real first line measured 18,139 bytes), and `readCodexRolloutCwd`'s old fixed 8KB read parsed a truncated line and answered null for EVERY rollout on that version. That one null unplugged the whole codex identity pipeline: the provider linker got no candidates (no pane ever named, which Pat experienced as a codex window stuck on "has not named its session yet" while the session wrote a 4.5MB conversation unseen), and `findFreshTranscript`'s codex cwd guard skipped every candidate. The reader now consumes the ENTIRE first line, chunked in the byte domain and decoded once; never head-read-and-parse a codex meta line with a fixed buffer (`provider-history.js`'s 256KB line-split head is the ruled-out sibling, 14x today's size). Two rules shipped with it, both from the same incident. **The tile and the visible-pane registration make ONE terminal decision** (`renderer/stage/terminal-view.cjs`): the tile drew a fallback terminal for `tty` OR the codex fallback while `ttyPaneIds` registered only `tty`, so a fallback xterm had no observer, no backfill, no frames, an empty black box over a live session. **And a `live:<paneId>` window upgrades exactly like a `pane:<paneId>` window** (`provisional-upgrade.cjs` handles both prefixes): when the linker lands, the live: rail row BECOMES the real-id row, so a live: window that cannot upgrade stops resolving a session and Stage drops it mid-look, which would have traded the stuck note for a vanishing window. The registration half is proven two-sided (reverting the filter fails the backfill assertion). **The same codex release also moved the CONVERSATION (2026-08-08, found when Pat asked for his review session back and the fixed window would still have opened without his prompt or the verdict).** 0.147.0 stopped writing `event_msg` `user_message`/`agent_message`; the conversation is now the `item_completed` item stream (`item.type` `UserMessage`/`AgentMessage`, text in content parts whose `type` casing differs by role: 'text' vs 'Text'). `applyCodexLine` parses exactly those two item kinds: `CommandExecution` items mirror the `custom_tool_call` lines already rendered (parsing both doubles every action row), and the `response_item` `message` lines are NOT the conversation, they carry injected scaffolding (skills instructions, AGENTS.md, environment_context) that would bury the real prompt. The old event shapes stay supported for the historical corpus. This also healed rail titles for new codex sessions, because `provider-history` reads the first user block through the same parser. When codex updates, diff a REAL fresh rollout's event types against `applyCodexLine` before trusting any codex surface.
