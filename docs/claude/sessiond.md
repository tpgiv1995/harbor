# Harbor doctrine: sessiond, keepers, and session lifecycle

Part of CLAUDE.md. The single file crossed the Claude CLI's 150k-char auto-load limit on 2026-08-29, so the per-area doctrine moved here VERBATIM; nothing was rewritten. Everything below carries the same force as CLAUDE.md itself. Read this file BEFORE touching `app/src/daemon/` (daemon, keeper, dormancy, orphan sweep, boot-id, daemon-watch), `app/src/main/session-daemon/`, `bin/harbor-sessiond`, resume redelivery, liveness or reconcile logic, or worker close.

- **Sessiond is the ONLY session backend (2026-08-14).** `session-daemon/factory.js` `resolveSessionBackend` accepts exactly `sessiond`; `HARBOR_SESSION_BACKEND=herdr` throws the retirement error by name, and any other value fails closed with what was got. That is deliberately an exact-match check and not a fallback, the same fail-closed-allowlist posture the old protocol check taught (never widen a compatibility decision by comparison operator; a value nobody recognizes gets read by a human, not accepted for looking plausible). The factory also enforces the session-store policy (`SESSION_STORE_BLOCKED`) before handing out a client or supervisor.
- **Never start the daemon except via `bin/harbor-sessiond start`, and liveness is a REAL REQUEST, never a status reply.** `daemonHealthy` sends a timed `health` request to the socket; the socket file existing proves nothing (`probeLiveOwner`'s named-pipe trap, 2026-08-07 sibling fix) and a reply a dead process can still produce proves less (the herdr wedge lesson, kept in `docs/CLAUDE-md-archive-linux-era.md`). The start path carries the ALREADY-RUNNING GATE (2026-08-06): it used to start unconditionally and the new daemon deleted the live socket and rebound it, twenty-eight daemons deep with twenty-seven orphaned. `started: true` means the daemon ANSWERED a real request within `HARBOR_SESSIOND_READY_TIMEOUT_MS`, never that it was forked. The env the daemon gets is `cleanDaemonEnv`'s small allowlist (a daemon started with a session's environment leaks that session's ids into every pane it spawns); on win32 that includes COMSPEC/SystemRoot/PATHEXT (a pty needs a shell) and the user's full PATH (2026-08-13: a hand-built PATH starved every statusline tee, so the context and usage meters froze). **`ELECTRON_RUN_AS_NODE` is forwarded when the caller set it** (2026-08-12): without it the daemon and every keeper ran as FULL Electron apps, a GPU process and a network service per daemon, and an uncaught keeper exception raised Electron's MODAL ERROR DIALOG instead of writing stderr and exiting, so a failed pty spawn looked like "keeper never came up within 7000ms" with an empty log while a dialog sat over the desktop. The daemon store defaults to `~/.local/state/harbor/sessiond` (`HARBOR_SESSIOND_DIR`/`HARBOR_SESSIOND_SOCKET` relocate it); on win32 the "socket" binds as a named pipe DERIVED from the socket path by hash (`src/daemon/paths.js` `listenAddress`, 2026-08-06: Node's net on win32 only speaks pipes, and a filesystem path fails as a misleading `listen EACCES`), flat-namespace-safe so a relocated harness store can never collide with the real one. On POSIX the AF_UNIX 108-byte `sun_path` limit is handled at the same layer (a too-long path binds TRUNCATED without erroring; measured).
- **The daemon leaves its pulse and its last word (2026-08-14).** Two silent daemon deaths that day took 15 and then 8 ConPTY trees, and nothing anywhere recorded that the daemon had died, let alone why. `src/daemon/daemon-watch.js` is the exit-capture watcher: the detached start spawns it as the daemon's PARENT (it must be the parent or Windows discards the only exit code and signal Node can see), and it appends one honest line to `sessiond.log` on every exit: pid, code, signal, uptime, and `kind=clean|crash`, where clean means exit 0 OR a REQUESTED stop (Windows reports a requested child termination as code 1 with no signal, so the observed request is the only honest discriminator; the daemon IPCs `clean-shutdown` and the watcher records forwarded SIGTERM/SIGINT). The daemon itself logs an RSS heartbeat (`rss pid=... rss_bytes=... heap_used_bytes=... sessions=...`) every 60s (`HARBOR_SESSIOND_RSS_INTERVAL_MS`), so the NEXT unexplained death has a memory trend leading up to it instead of silence. Never route daemon stderr to the void; the log is the whole forensic record.
- **AN IDLE SESSION IS ENDED ON WINDOWS TOO, AND EVERY SESSION EXIT LEAVES A LOG LINE (2026-08-20).** Dormancy (the 2026-08-09 "an idle session is not a free session" feature) was silently INERT on win32 for its whole life here: its cpu signal read `/proc/<pid>/cgroup`, which does not exist on Windows, answered null, and null honestly means "busy, never sleep", while the boot line said "dormancy on". Sessions therefore accumulated until 27 claude runtimes plus ~190 private stdio-MCP node children held ~39GB of an 87GB commit limit; the machine spent 2026-08-20 at the ceiling (Resource-Exhaustion-Detector events 09:41/14:28/17:59, kernel live dumps, a reboot), and CLI processes died of failed allocations at the exact moment a turn started. Pat experienced that as **"messages get hung"**: the prompt reaches the transcript (user record + LAST-PROMPT written), the CLI dies within seconds, no reply ever comes, and the window keeps saying ready. Diagnosed from the retention math (exit.at inside the send's minute) because nothing else recorded the death, which is the second fix. The win32 cpu signal is now one `Win32_Process` snapshot per sweep summed over each session's keeper-rooted process TREE (the keeper is the CLI's direct parent under ConPTY, verified live; the tree is the per-session scope Windows actually has; stale ppids and recycled pids misread only toward busy, the safe direction), taken only when some session is past the pty-idle threshold, null (busy) on any probe failure, with the failure logged once. The boot line now NAMES the cpu source, and spec 7w is the win32 twin of the posix end-to-end spec 7: it fails at pre-fix HEAD on exactly "the idle session must be put to sleep". And because that day's dozen deaths left a log with 125 spawn lines and ZERO exits (state files and keeper logs are reaped 5 minutes after exit), `allStates()` now writes one `exit <id> pid= code= signal=` line per exit, deduped, driven even unattended by the RSS heartbeat (`test/daemon/exit-log.test.js`). A resume into such a session already redelivers the unanswered message (the 2026-08-14 bullet below), which is why Pat's hung prompts healed on retry; what was missing was the machine not eating the CLI, and the log not eating the evidence.
- **ORPHANED MANAGED PROCESSES ARE SWEPT, A LOST PTY EXIT IS FOUND, AND A NAIVE PARENT-DEAD TEST IS NEVER A KILL SIGNATURE (2026-08-20, the zombie-closure pass).** Zombies are this machine's oldest wound (28 orphaned daemons, harness daemons outliving killed runners, half-killed workers, ~190 MCP children at the commit peak), and the one vector every prior guard missed is a process WE manage whose parent dies too hard to run teardown: a SIGKILLed mcp-lazy-shim cannot stop its backend, a crashed claude cannot stop its MCP servers. `src/daemon/orphan-sweep.js` closes it with three fences proven necessary by the live audit that preceded it (a naive parent-is-dead test flagged the daemon's own keepers after a legitimate restart, plus half of Windows): PATTERN SCOPE (only the managed families are ever candidates), a PID-REUSE-AWARE orphan test (a parent created after its child is a recycled pid; unreadable creation times refuse), and TWO-SIGHTING HYSTERESIS. Kills are `taskkill /T` so a swept backend takes its own children (browsers) along; env `HARBOR_SESSIOND_ORPHAN_INTERVAL_MS` (default 5m, 0 off, win32 only) and `HARBOR_SESSIOND_ORPHAN_PATTERNS`. The same pass runs the DEAD-PTY REAP: ConPTY loses onExit for instant-exit children (measured near-always for `cmd /c exit 7`), the keeper's new `kill(pid,0)` child watch (`HARBOR_SESSIOND_CHILD_WATCH_MS`, seam `HARBOR_SESSIOND_TEST_DROP_PTY_EXIT`) covers that but goes BLIND when the freed pid is recycled, so the sweep's process table, which carries creation times, is the identity-verified backstop: a session whose child is absent or reborn after the session started is terminated through the keeper's own verified-gone path. Three mechanisms compose by ownership: keeper watch (event lost), table reap (keeper blind), periodic reconcile (keeper itself dead of a native ConPTY abort, seen live under harness churn). Two lessons paid for tonight: calling `decideKills` twice against one suspects map made each call wipe the other family's sightings, so a dead session reset to one sighting forever (one combined call now, spec 5b caught it pre-ship); and a bare `0 !== 1` assertion cost an hour of blind theorizing where a failure message carrying the state file and log tail answered it on first read (`exit-log.test.js` now does). Suites: `test/daemon/orphan-sweep.test.js`, `lost-exit.test.js`, and `exit-log.test.js` green 10/10 under the churn that exposed all of it.
- **A resume REDELIVERS an unanswered human message, never a generic nudge over it (2026-08-14).** The same double-crash left sessions whose transcript tail was a typed human message Claude never answered. A bare resume then added an isMeta nudge record, and the Claude CLI answered it CLIENT-SIDE with a synthetic "No response requested", which swallowed the real question: the session read as answered while Pat's message had never reached the model. `main/resume-nudge.js` `planResumeNudge` reads the transcript tail: an assistant tail gets the plain nudge; a human-typed tail (`origin.kind === 'human'` or `promptSource === 'typed'`) is REDELIVERED verbatim as the resume's message; a meta user record stops the scan so a prior nudge can never become a redelivery loop; and a human tail carrying non-text parts REFUSES with an honest message ("reattach it and send the message again"), because an attachment cannot be safely re-sent from the transcript. An unreadable tail keeps the exact historical bare-resume behavior instead of making every resume fail. `session-send.js` `resumeNudgePlan` is the one caller.
- **A SESSION CANNOT OUTLIVE ITS BOOT, and the store said thirteen did (2026-08-07).** The same family as the dead-shell guard (`docs/claude/conversation.md`), arriving through Harbor's own daemon. Pat restarted his machine when he got to work; Harbor came back showing **"13 live"** over thirteen sessions that had died with the boot seven minutes earlier, described one of them as ACTIVE and `ready`, and accepted two sends into a pane with no process behind it ("could not confirm the message reached the session"). He reasonably asked whether his work network was at fault. It was not, and that is worth stating because the transcript ALSO held one `API Error: Unable to connect to API (ENOTIMP)`: that was a single transient DNS blip half an hour earlier, and at diagnosis time 30 of 30 probes were clean with every record type NOERROR from both resolvers. A visible error near a failure is not the failure. The cause: `keeper.js` writes `exit` from `terminal.onExit`, and a reboot kills the keeper cold, so that line never runs and the state file survives saying `exit: null` with a pid from the dead boot. `allStates()` reaped only sessions carrying an exit, so all thirteen came back from disk as live. **The pid is NOT the discriminator** (pids are reused across a reboot, so `kill(pid, 0)` eventually answers "alive" about an unrelated process, which is worse than the bug it fixes); the BOOT is, and `src/daemon/boot-id.js` states it (`/proc/sys/kernel/random/boot_id` on Linux, derived from the boot instant elsewhere with a tolerance for clock adjustment). Two guards, because the stamp cannot see everything: `allStates()` FILTERS a state whose boot has ended (hot path, so synchronous and exact, and filtering rather than deleting is harmless even if a verdict were wrong), and `reconcileStaleSessions()` runs at startup, after the already-running gate (which is what proves nobody else owns these keepers) and before serving (the first thing a client asks is `list`), catching what the stamp cannot: a keeper killed WITHIN this boot, by asking the keeper socket the way this file already asks its own, since **liveness is a real CONNECTION and never a file existing**. Only a session proven dead is written to, which is what makes writing another process's state file safe. The synthesized exit carries `code: null, signal: null` and a reason, because nobody watched these die and a fabricated clean exit would read as an ordinary close downstream. The app side needed NO change: `snapshotFromSessions` already filters on `exit`, so it was simply being fed a lie by the daemon; fix this layer, not that one. Sibling fixed the same commit: `probeLiveOwner` short-circuited on `fs.existsSync(socketPath)`, the named-pipe trap `keeperIsUp` documents ten lines above it, so on Windows the daemon's own already-running gate would answer "dead" about a live owner. Specs 4 and 5 in `app/test/daemon/sessiond.test.js` are two-sided and were run against the old code (they fail there, pass here): the stale session is reproduced as a reboot actually leaves one, and the exit REASON is asserted so the proof cannot pass on the keeper probe alone, while a control session must survive, keep its pid and stay drivable.
- **A spawn is never abandoned, a keeper never dies of a socket error, and "exited" surfaces within a minute (2026-08-09).** Three platform-neutral guards from the shared-cgroup meltdown (the Linux containment half, systemd scopes and oomd, is in `docs/CLAUDE-md-archive-linux-era.md`; `session-scope.js` honestly reports `not linux` on this box). `reapAbandonedSpawn` in daemon.js: a spawn that misses its deadline is put down (SIGKILL, late-bound state marked exited, files cleaned), never abandoned, because an abandoned child boots late as a live ghost, and one that day held `--resume` of the session Pat was about to retry, a double-writer in waiting (`test/daemon/spawn-reap.test.js` reproduces the stall with a keeper slowed by a NODE_OPTIONS require hook). keeper.js carries the client-socket 'error' listener (`test/daemon/keeper-crash.test.js` reproduces the exact production stack: a peer that closes with the keeper's reply unread surfaces as `read ECONNRESET`; three LIVE keepers died of it that night). `startPeriodicReconcile` (60s, `HARBOR_SESSIOND_RECONCILE_INTERVAL_MS`): a keeper killed within this boot surfaces as exited without waiting for the next daemon start (`test/daemon/within-boot-honesty.test.js`); before it, the daemon listed three dead sessions as live for 25 minutes. Never remove the reap or the periodic reconcile.
- **Worker close verifies the PROCESS died, not just the pane.** `closePaneTab` captures the pane's pid (via `processInfo`) BEFORE closing, because a clean tab-close removes the pane from the daemon while its `claude --resume` process (and its stdio MCP children) can survive the pty teardown. Pane-absence alone is a HALF kill; when the captured pid outlives the close, it escalates to an exact terminate on the process tree and re-verifies, so `verified: true` always means the process is gone. The `+signal` method suffix records that escalation ran.
- **The daemon suite family is FULLY PORTED on win32 (2026-08-30, sessiond-ng program).** All test files spawn daemons/keepers/stand-ins through `test/support/gui-node.js` (GUI-subsystem Electron-as-node, the 2026-08-12 production pattern), which is the WINDOW-FLASH floor: a console-subsystem child on this machine opens a visible Windows Terminal window, and windowsHide only covers the direct spawn. Single-instance ownership is proved by connect plus bind refusal on the `listenAddress`-derived pipe (a pipe leaves no file and cannot go stale on disk); socket-path keeps its AF_UNIX path-limit assertions behind POSIX guards and proves win32 connectability plus EADDRINUSE for a second owner; cli runs every script through the node runner with health-connection readiness; sessiond's real-daemon cluster uses real-tmp stores and connect probes; session-scope and the systemd cases print honest win32 skips; `new-session-usable` skips honestly on win32 (the native claude.exe aborts 0xC0000409 under an isolated fresh-config ConPTY; the first-run proof stays POSIX-only) and spawn-reap's harness remains POSIX-only. `scripts/test.js` filters match repo-relative paths in either separator spelling. The three porting rules stand: liveness is a real CONNECTION, never a file existing; a suite's daemon cleanup registers BEFORE its readiness wait (a leaked child keeps node --test alive FOREVER); a pty session is terminated through the daemon before its store dir is deleted (an orphan ConPTY cmd.exe holds the dir as cwd and rmSync EPERMs forever).
- **ONE WIN32 SESSION IS ONE NAMED JOB OBJECT (2026-08-30).** `src/daemon/win-job.js` (koffi 3.1.6, explicit-offset structs measured under BOTH system Node and Electron-as-node; the r1 measurement record lives in the orchestration research) gives each session `Local\harbor-session-<id>-<hash(store)>`. The daemon creates the job UNARMED and assigns the keeper right after spawn (children join automatically, the ConPTY host included); the KEEPER arms `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` only once it holds a handle of its own (f8 finding M1: a daemon dying as SOLE holder must not take the live session with it), so with both holders alive either keeps the name open for a successor (the name dies with the last handle, measured) and the kernel reaps the whole tree the instant both are gone, closing the 2026-08-14 double-crash orphan vector at the kernel. `putDownKeeper` and `reapAbandonedSpawn` kill by job first with the process paths as fallback; the keeper terminates its own job in `finishExit`, strictly AFTER the exit record persists and the exit-delay lets observers drain (f8 finding H2: the first shape terminated on the next tick, killed the keeper before the record was written, and every deliberate ending read as a crash); dormancy's cpu signal prefers job accounting (microseconds, monotonic, includes exited children) and the boot line names the active source. A relocated store must name `HARBOR_SESSIOND_JOB_NAMESPACE` or runs without jobs, the slice rule's twin. `HARBOR_SESSIOND_SESSION_JOB_MEMORY_MAX` is opt-in and OFF by default: a Windows job memory limit DENIES ALLOCATIONS rather than selecting a victim, so exhaustion can starve the keeper before it records an honest exit; ship telemetry, not default ceilings. `removeSessionFiles` drops the daemon's job handle at exit-retention reap or the handle map grows per exited session forever.
- **PROCESS QUESTIONS ANSWER FROM RESIDENT MEMORY, NOT A POWERSHELL SPAWN (2026-08-30).** `src/daemon/process-intel.js` keeps an NtQuerySystemInformation snapshot in the daemon (2s refresh, 5s stale REFUSAL, boot-time self-check against the undocumented struct layout, lazy cmdline via NtQueryInformationProcess(60) cached by pid+creation FileTime, pid-reuse identity per orphan-sweep's rules). Daemon verbs `proc-info`/`proc-tree`/`proc-find` answer in about 1 to 11 ms where a CIM spawn measured 2.5 to 3.6 s; dormancy's fallback cpu table and the orphan sweep read native rows first with the CIM paths kept as fallback behind one honest log line, and the app's win32 platform asks the daemon on a 2s budget before falling back to the unchanged CIM 20s-deadline doctrine, so a daemonless Harbor behaves exactly as before. WMI eventing was REJECTED on measurement (a `WITHIN 1` subscription burns roughly a third of a core forever) and Win32_ProcessStartTrace needs elevation this daemon does not have.
- **Exit records never carry JS undefined (2026-08-30).** ConPTY's onExit after `terminal.kill()` often delivers exitCode/signal as undefined; JSON.stringify then DROPS the keys and the log printed the word undefined on every dormant exit. The keeper normalizes onExit values to number-or-null (signal keeps number|string), matching the synthesis paths' honesty, and `noteExitObserved` prints null for legacy keyless records. The two-sided proof forces the ConPTY undefined shape through a keeper-only require hook (`exit-undefined-honesty.test.js`).
- **NEVER `npm ci` THE LIVE DAEMON'S OWN node_modules (2026-08-30, live near-miss).** `npm ci` deletes the tree first; the running keepers' mapped `conpty.node` EPERM'd the delete midway and left node-pty's package.json GONE while the daemon looked healthy, which would have made every NEW session spawn die of MODULE_NOT_FOUND. The daemon and its keepers survive (code already mapped), which is exactly what makes the breakage invisible until the next spawn. Install additively (`npm install`) or copy files in; recover from any intact copy with robocopy, where only the still-mapped native binary fails harmlessly in place.
- **The daemon heals itself, and the gate answers three verdicts (2026-08-30).** `daemon-watch.js` is a supervisor, not just exit capture: a real-request health probe on a slow clock, N consecutive COMPLETED-and-failed probes = wedge (never a wall-clock gap: machine sleep freezes prober and daemon together), SIGKILL of its own child, a third exit kind `kind=wedge`, pipe-release wait, respawn with backoff and a give-up cap (`HARBOR_SESSIOND_RESPAWN_MAX` per 15 min; `=0` restores exit-capture-only); a crash respawns too; a clean stop or `yield` NEVER respawns, which is what lets a handover retire the old watcher. The gate (`probeStoreOwner`) sends a real health request: `ok` exits 3 unchanged, `mute` exits 4 by name and never unlinks or binds (a wedged owner is `recover`'s to kill, with owner.json identity verification: the daemon by pid plus creation time plus exec name, the watcher additionally by a command line naming daemon-watch (f8 finding H1: exec name alone matches every keeper, and a recycled watcher pid must never aim the kill at one), and any mismatch refuses), `dead` binds. Zero-drop is structural: keepers are independent pipe servers, the successor's reconcile writes only to sessions a real request proved dead, and session jobs reacquire by name (`HARBOR_SESSIOND_JOB_NAMESPACE` forwards through the CLI start so a relocated successor keeps containment). Proven two-sided in `test/daemon/handover.test.js` (same keeper pid, same pty pid, drivable through the successor; healer removed, the wedge persists forever), with the supervisor's edges in `self-heal.test.js`, the gate in `gate-verdicts.test.js`, the CLI lanes in `test/bin/handover.test.js`, and the app side in `test/main/wedge-recovery.test.js`.
- **Replacing the live daemon goes through `harbor-sessiond handover`, per `docs/SESSIOND-ROLLOUT.md`.** Identity snapshot, yield (the incumbent finishes in-flight requests, closes its server, IPCs clean-shutdown; a pre-yield incumbent falls back to the `shutdown` verb, expected exactly once on the first swap, verdict `yielded: false`), pid-gone and pipe-release waits, start, pid-map parity verdict; a refusal at any unverifiable step leaves the incumbent running. The app watchdog heals a wedge IN PLACE (`main/wedge-recovery.js`: recover-mode connect plus `terminalBridge.reconnectNow`); `app.relaunch` is gone from the wedge path and survives only in `daemon:retry` as the manual last resort.
- **THE KEEPER DIES WITH ITS HARNESS TOO, BECAUSE THE DAEMON MAY NOT LIVE LONG ENOUGH TO REAP (2026-09-03).** The harness reaper above is real and its spec passes, and three crashed probe scripts still left three keepers and three claude trees alive for an hour that evening. The gap is the crash SHAPE: the spec's stand-in harness is a separate process, so the daemon outlives it and reaps; a real harness is the daemon's own spawner, and on Windows libuv puts a non-detached child in a job object with kill-on-close, so the daemon is gone within a second of its spawner with nothing logged (`test/support/crashing-harness.js` reproduces it: stdio to files, empty stderr, no reap line), its two-second watch never fires, and the keepers, spawned detached, survive with their sessions. The daemon now writes the harness pid into each session's config (`harness_pid`, from the same `resolveHarnessWatchPid`) and the KEEPER watches it: two sightings, then an honest exit record (`reason: harness died; session reaped by its keeper`), the pty killed, `finishExit` so a session job takes the tree. The default store never carries a harness pid, so production keepers never do this. Two-sided in `test/daemon/keeper-harness-reaper.test.js`: pre-fix it fails on "the session should die with its crashed harness". Two habits for anyone writing a harness script: name `HARBOR_SESSIOND_JOB_NAMESPACE` (a relocated store has no kernel containment without it) and run teardown in a `finally` (`scripts/drive-ask-sheet-win.js` shows both). **A suite whose sessions run with the STORE as cwd must wait for the pty child to be gone before deleting the store** (the ConPTY cmd.exe holds the directory; `sessiond.test.js`'s cleanup EPERM'd about one run in five until it polled the child pids and deleted with retries). **And a main-process test must inject `daemonRequest`** when it builds a win32 platform adapter: the adapter's default asks the REAL user daemon for process intel, which answered "not alive" for the tests' fictional pids and failed four platform specs on the gate machine.
- **THE MODELED SCREEN AGREES WITH CONPTY ABOUT HOW WIDE A GLYPH IS (2026-09-03, live-caught off Pat's Data-Mapper-Live pane, reproduced against the real CLI in an isolated daemon).** `src/daemon/screen.js` built xterm-headless with its default Unicode 6 width table, on which `❌`, `✅` and every emoji are ONE cell; ConPTY counts them as two, writes a full-width row, and trusts the terminal to wrap at the edge. The modeled row therefore ended a cell short, never wrapped, and the next row's first character was painted onto the previous row's last column; every emoji-bearing full-width row shifted everything under it one more column left until ConPTY next positioned the cursor absolutely. A pasted prompt holding three `❌` rows shifted the three rows under it by one, two, then three columns; on his pane the table above an AskUserQuestion dialog shifted the option rows so the parser lost options 1 to 3 (the card side of that incident is in `docs/claude/conversation.md`). Every reader of the pane (menu-parse, the composer and dead-shell guards, classifyBlocked, the readiness waits) was reading a subtly wrong screen whenever an emoji sat in a full row above. The fix loads `@xterm/addon-unicode11` (packed into `src/daemon/package.json`; installed ADDITIVELY, never `npm ci`, per the bullet above) and sets `unicode.activeVersion = '11'`, the pairing VS Code ships with ConPTY, and passes `windowsPty: { backend: 'conpty', buildNumber }` on win32 so xterm's ConPTY resize heuristics are on. `test/daemon/screen-width.test.js` is two-sided: an ASCII full row wraps either way (the control), a full row ending in `❌`/`✅`/`📊` wraps the next character to column 0 only with the fix, and three such rows over an option row leave the option at column 0. Synthetic pass-through output never reproduces this (ConPTY ends short rows with explicit positioning); the trigger is a FULL-WIDTH row, which the real CLI produces for wrapped prose and pasted input.
- **Provider sessions are first-class in the daemon lifecycle (2026-08-30; the launch/identity half lives in `docs/claude/providers.md`).** The keeper's `annotate` verb late-binds `agent`/`agent_session` onto the persisted state with the same allowlist posture as exitAnnotation (only those two fields; foreign fields refused; same-provider rebind allowed for codex `/new`); the app-side linker annotates on pairing and the sessiond client emits `pane.updated` for same-pane identity changes. Dormancy's transcript veto routes by provider in `sessionWorkFresh`: codex rollouts and cursor transcripts are judged by their newest RECORD (never mtime; cursor records commonly lack timestamps, so an observation map tracks record progress), roots default to `~/.codex/sessions` and `~/.cursor/projects` (`HARBOR_CODEX_SESSION_ROOTS`/`HARBOR_CURSOR_TRANSCRIPT_ROOTS` override), and an unresolved identity or unlocatable transcript THROWS, which the sweep reads as leave-it-alone: a provider pane that cannot be resumed is never put to sleep. `awaitingAnswer` carries provider dialog markers captured from real screens.
